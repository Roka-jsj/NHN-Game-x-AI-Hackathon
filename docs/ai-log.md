## 2026-08-01 (D-9) — 패스 0 · 배포 캐너리 — 지휘: A

### 내린 지시

「전문가 빌드 프롬프트 세트」의 프롬프트 0을 그대로 집행했다.
지시의 핵심은 만들라는 것보다 **만들지 말라는 것**이었다 —
"게임을 만들지 마라. 기능을 넣지 마라. 이 파일 3개 외에 아무것도 만들지 마라."

만든 것은 3개뿐이다.

- `index.html` — `<h1>RISING</h1>` 과 `<p>D-9 canary</p>` 두 줄. 그 외 아무 내용 없음
- `docs/ai-log.md` — 이 파일
- `README.md` — 팀 롤(A=빌드 / B=검증), 저장소 구조, URL 자리

`index.html`에 강제한 조건:

- `viewport` 에 `viewport-fit=cover, user-scalable=no`
- body 에 `touch-action: manipulation`, `user-select: none`,
  `-webkit-tap-highlight-color: transparent`, `margin: 0`
- 배경 `#12242E`, 글자 `#F4F7F5`

이 4줄은 캐너리에 넣을 이유가 없어 보이지만 넣었다.
모바일 제스처 차단(게이트 #5)은 나중에 붙이면 "왜 확대가 되지" 를 디버깅하게 된다.
지금 넣으면 0초, 나중에 넣으면 30분이다.

### AI가 틀린 것

**저장소가 완전히 비어 있다는 사실을 확인하기 전에 계획을 세울 뻔했다.**
커밋 0개 · 브랜치 0개였다. 기본 브랜치조차 없었다.
이건 계획에 실제로 영향을 준다 — GitHub Pages 는 브랜치에서 서빙되는데,
첫 푸시된 브랜치가 기본 브랜치가 되어버린다.
작업용 브랜치(`claude/document-work-icemu4`)가 기본 브랜치가 되면
문서가 말한 "성역 URL" 이 throwaway 브랜치에 묶인다.

확인 후 사람에게 물어 `main` 을 함께 만들기로 확정했다.
**묻지 않고 진행했으면 URL 이 작업 브랜치에 묶인 채로 9일을 갔다.**

### 어떻게 교정했나

동일 내용을 `main` 과 작업 브랜치 양쪽에 푸시했다.
Pages 는 `main / (root)` 에서 서빙한다. 작업 브랜치가 사라져도 URL 은 산다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

| 게이트 | 항목 | 상태 | 값 |
|---|---|---|---|
| #8 | 콘솔 청결 | 자동 측정 대기 | 패스 1 이후 헤드리스로 측정 |
| #9 | 링크 접근성 | **사람 확인 필요** | Pages 활성화 후 B가 폰 LTE로 |

**이 시점에 통과했다고 말할 수 있는 게이트는 하나도 없다.**
Pages Source 스위치는 GitHub 설정 UI 에서만 켤 수 있고 (이 세션의 GitHub 도구에 Pages API 가 없다),
폰 LTE 접속은 사람만 할 수 있다.

문서가 정의한 D-9 하드컷은 "캐너리 URL 이 B의 폰 LTE 로 열림" 이다.
**저장소 상태로는 준비가 끝났지만, 하드컷 자체는 아직 통과하지 않았다.**
스위치 하나 + 폰 하나가 남아 있다. 이 둘이 D-9 안에 끝나야 한다.

### 남은 부채

- **git 태그를 원격에 올리지 못한다** — 커밋 직후 발견했다.
  이 세션의 git 프록시는 `refs/heads/*` 푸시는 통과시키지만 `refs/tags/*` 는 403으로 거부한다.
  4회 재시도 모두 동일한 403이므로 일시적 오류가 아니라 정책이다.
  **태그 대신 커밋 SHA를 롤백 지점으로 README 에 표로 남긴다.**
  사람이 로컬에서 `git tag <이름> <SHA> && git push origin --tags` 로 한 번에 만들 수 있다.
  태그가 롤백 지점 역할을 하는 건 변함없다 — 지금은 이름이 SHA일 뿐이다.
- **Pages Source 활성화 (사람)** — Settings → Pages → `main` / `(root)`
- **URL 을 README 최상단에 기입 (사람)** — 지금은 자리 표시자다
- **B의 폰 LTE 접속 확인 (사람)** — 이게 되어야 배포다. 와이파이는 증거가 아니다
- 공식 페이지에서 신청서 양식·팀 인원 조건 직접 확인 (사람)
- A·B 각각 최소 1커밋 — AI 커밋은 사람 커밋을 대신하지 못한다.
  2인 팀 롤 기술서의 증거는 사람의 커밋 로그다

## 2026-08-01 (D-8 작업을 D-9에 선행) — 패스 1 · 코어 루프 — 지휘: A

### 내린 지시

프롬프트 1을 그대로 집행했다. 지시의 무게중심은 게임이 아니라 **네 가지 구조**에 있었다.

1. 고정 타임스텝 + 누산기 (delta 250ms 클램프, 렌더 보간, visibilitychange 리셋)
2. 입력 큐 (핸들러는 큐에 넣기만, 프레임 시작에서 소비, `event.timeStamp` 사용)
3. 상태 기계 (전이는 한 곳에서만)
4. devicePixelRatio 는 resize 에서만

만든 파일: `index.html`, `src/config.js`, `src/main.js`, `src/game.js`.
연출·성능·난이도·색·소리는 전부 뒤 패스 몫이라 손대지 않았다.
발판 배치는 고정 패턴 8개 하드코딩, 랜덤 0.

### AI가 틀린 것

**① 문서의 「발판 두께 12」를 그대로 착지 허용폭으로 쓰면 게임이 성립하지 않는다.**

두께 12 → 반두께 6 → 허용 ±6px.
그런데 같은 문서가 정한 조준 진동 진폭은 `조준선 길이 × 0.06` 이다.
420px 최대 도약에서 진폭은 ±25.2px — **허용폭의 4배**다.
원거리 도약은 사인파를 완벽하게 읽어도 산술적으로 착지가 불가능하다.

수치를 의심하지 않고 그대로 구현했으면 "구현은 스펙대로인데 게임이 안 되는" 상태로
D-7 게임필 패스까지 갔을 것이다. 거기서 발견하면 물리 수치를 되돌려야 하고,
물리 수치는 패스 2가 보호해야 할 영역이다.

**② 첫 60Hz/120Hz 측정에서 발판 수가 49 / 51 로 갈렸다 (오차 4.08%, 목표 3% 미만).**

게임의 고정 타임스텝을 의심했다. 그런데 시뮬레이션 틱은 **1799 / 1799 로 완전히 동일**했다.
틱이 같은데 결과가 다르면 게임이 아니라 입력이 다른 것이다.
원인은 내가 만든 측정 봇이었다 — 봇이 매 렌더 프레임마다 판단해서
120Hz 회차에서 두 배 자주 폴링했고, 그만큼 반응이 빨라졌다.
**사람의 반응 속도는 주사율에 비례해서 빨라지지 않는다.** 측정 도구가 틀렸다.

멀쩡한 누산기를 "고쳤으면" 진짜 버그를 심을 뻔했다.

### 어떻게 교정했나

**①** 착지 허용폭을 `발판 반두께 + 플레이어 반지름` = **20px** 으로 정의했다.
플레이어는 점이 아니라 반지름 14의 원이므로 원의 가장자리가 발판에 걸리면 붙는 게 물리적으로 맞다.
`aimError` 도 이 값으로 정규화한다 — 디렉터의 임계값 0.4 / 0.6 이 의미를 갖는 유일한 기준이다.

수치 검산:

| 도약 거리 | 진동 진폭 (×0.06) | 허용폭 | 결과 |
|---|---|---|---|
| 90px (근거리) | ±5.4px | ±20px | 위상과 무관하게 붙는다 |
| 240px (중거리) | ±14.4px | ±20px | 대충 눌러도 붙는다 |
| 420px (원거리) | ±25.2px | ±20px | **사인파를 읽어야만 붙는다** |

문서가 의도한 "근거리는 거의 안 흔들리고, 원거리는 크게 흔들린다"가 수치로 성립한다.
완벽 착지(중심 ±12%)는 ±2.4px — 근거리에서도 타이밍이 필요하다.

**②** 봇의 판단을 화면 주사율이 아니라 **고정 60Hz 격자**에 묶고,
주입하는 `timeStamp` 도 격자 시각으로 고정했다.
이제 두 회차의 입력 스트림이 완전히 동일하므로, 차이가 나면 그건 게임 탓이다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

`tools/smoke.mjs` — Playwright + 합성 클록(rAF·performance.now 스텁) 헤드리스 하네스.
실기기 120Hz 화면이 없어도 게이트 #1 을 실제로 잴 수 있다.

| # | 항목 | 측정값 | 판정 |
|---|---|---|---|
| 1 | 60Hz vs 120Hz 속도 동일성 | 30초 후 도달 발판 **49 / 49 (오차 0.00%)**, 시뮬 틱 **1799 / 1799** | 통과 (목표 <3%) |
| 3 | 탭 전환 복귀 (30초 방치) | 복귀 후 틱 1197 / 정상 1200 (**편차 0.25%**), 누산기 잔여 16.667ms | 통과 |
| 8 | 콘솔 청결 | 에러·경고 **0개** | 통과 |
| — | 루프 왕복 | 방치 32초 → 사망 관측, 입력 1회로 재시작, 판수 2 | 통과 |

**틱 1799 / 1799 가 이 패스의 핵심 증거다.** 30초 × 60Hz = 1800 스텝이고,
어떤 주사율에서 돌려도 시뮬레이션이 정확히 같은 횟수만큼 돌았다는 뜻이다.
심사자 모니터가 60Hz인지 144Hz인지 몰라도 된다.

### 남은 부채

- 게임필이 전무하다 — 히트스톱·입력버퍼·코요테·스쿼시 전부 패스 2
- 렌더 코드가 `main.js` 안에 있다. 패스 3에서 오프스크린 배경과 함께 `render.js` 로 분리한다
- `tools/smoke.mjs` 는 프롬프트 1의 파일 목록에 없는 파일이다.
  하지만 "60Hz와 120Hz에서 오차 3% 미만"은 프롬프트 1이 스스로 요구한 완료 조건이고,
  실기기 없이 그걸 잴 유일한 방법이었다. 게임은 이 파일을 로드하지 않는다
- 실기기 확인 0회 — iPhone·Android 둘 다 아직 안 돌렸다 (게이트 #4·#5·#7)
- 물 근접·사망 연출이 없어 지금은 죽어도 밋밋하다. 패스 2·5·6에서 붙는다

## 2026-08-01 (D-7 작업을 D-9에 선행) — 패스 2 · 게임필 — 지휘: A

### 내린 지시

프롬프트 2를 순서대로 집행했다. 이 프롬프트의 핵심은 목록이 아니라 **순서**다 —
효과 크기 순으로 배열돼 있고, 시간이 모자라면 아래쪽이 잘린다.

| | 항목 | 상태 |
|---|---|---|
| ① | 히트스톱 (착지 3f / 완벽 6f / 사망 8f→0.15배속 400ms / 신기록 4f) | 완료 |
| ② | 입력 버퍼 6프레임 | 완료 |
| ③ | 코요테 5프레임 | 완료 (패스 1에서 이미 시뮬레이션에 들어가 있었다) |
| ④ | 스쿼시 & 스트레치 | 완료 |
| ⑤ | 스크린 셰이크 (3/5/12/6, 감쇠 0.85, 사망 시 회전, 물 근접 상시 미세진동) | 완료 |
| ⑥ | 이징 (UI·스쿼시 easeOutBack / 링 easeOutCubic / 조준선·물은 선형 고정) | 완료 |
| ⑦ | 진동 조준 (사인파, 진폭 = 길이×0.06, 주기 620ms) | 완료 (패스 1에서 선행) |
| ⑧ | 파티클 (6 / 12 / 20, 배열 재사용) | 완료 |
| ⑨ | 트레일 4프레임 · 카메라 리드 | 완료 |

**하나도 버리지 않았다.** ③⑦이 패스 1에 먼저 들어간 건 둘 다 착지 판정 자체에
관여하는 시뮬레이션 규칙이라, 연출 레이어로 미루면 물리를 두 번 고쳐야 했기 때문이다.

건드리지 않은 것: 고정 타임스텝 누산기, 입력 큐 구조, 상태 기계 전이 규칙, 물리 수치.
게임필은 `src/feel.js` 라는 별도 레이어에 있고, 이벤트를 받기만 한다.

### AI가 틀린 것

**① 입력 버퍼를 "누른 것만 기억"으로 만들면 짧은 탭이 무한 차지로 남는다.**

문서는 "착지 6프레임 전에 들어온 입력을 기억했다가 착지 즉시 차지를 시작한다"고만 썼다.
그대로 만들면 이런 일이 생긴다 — 도약 중에 톡 눌렀다 뗀다 → 누른 건 버퍼에 남고
뗀 건 CHARGING 상태가 아니라 버려진다 → 착지하는 순간 차지가 시작되는데
플레이어 손은 이미 화면에서 떨어져 있다 → 1200ms 오버차지 강제 발사까지 끌려간다.

**릴리스도 같이 기억해서 착지 시점에 그대로 재현**해야 한다.
플레이어가 실제로 누른 시간만큼 차지하고 즉시 발사된다.

**② 60Hz/120Hz 완벽 착지 수가 3 / 5 로 갈렸다. 첫 가설이 틀렸다.**

`frameSimBase = game.simTime` 으로 잡고 있었는데, `simTime` 은 "마지막으로 시뮬레이션된
순간"이고 누산기에는 아직 시뮬레이션되지 않은 시간이 0~16.7ms 담겨 있다.
즉 기준점이 매 프레임 누산기 잔여분만큼 뒤처져 있었고, **그 잔여분은 주사율마다 다르다.**
조준 진동 위상이 그만큼 흔들리니 완벽 착지(±2.4px)가 갈린다 — 이게 첫 가설이었다.

`frameSimBase = game.simTime + accumulator` 로 고쳤다. 논리적으로 명백히 옳은 수정이다.
**그런데 다시 재보니 3 / 5 가 그대로였다.** 가설이 원인의 전부가 아니었다.

### 어떻게 교정했나

**②의 진짜 원인**은 따로 있었다. 입력은 프레임 시작에서 소비되는데,
그 시점에 시뮬레이션이 어디까지 진행돼 있는지가 주사율마다 최대 1스텝 다르다.
같은 입력이 60Hz에서는 착지 직전(→ 입력 버퍼 경로)에, 120Hz에서는 착지 직후
(→ 직접 차지 경로)에 소비될 수 있다. 두 경로는 차지 시작 시각이 다르고,
조준 진동은 절대 시각의 함수이므로 위상이 달라진다.

**이건 입력 버퍼가 있는 모든 게임에 내재된 성질이고, 고칠 대상이 아니다.**
차이는 최대 1프레임이며, 도달 발판 수(게이트 #1의 판정 기준)에는 영향이 없다 — 45 / 45.

진동 위상을 절대 시각 대신 **차지 경과 시간**의 함수로 바꾸면 이 차이가 사라진다.
검토했고, **버렸다.** 그렇게 하면 진동 위상과 도약 거리가 둘 다 "누른 시간"만의
함수가 되어 서로 완전히 종속된다. 자유도가 2개에서 1개로 줄고,
문서가 설계한 두 축("얼마나 오래 누를까" / "진동의 어느 순간에 뗄까")이 하나로 무너진다.
**측정값을 예쁘게 만들려고 게임을 망가뜨리지 않는다.**

`frameSimBase` 수정은 그대로 두었다. 원인의 전부는 아니었지만 그 자체로 옳다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

| # | 항목 | 측정값 | 판정 |

### 남은 부채

- **완벽 착지 수가 주사율에 따라 3 / 45 ~ 5 / 45 범위에서 흔들린다.**

### AI가 틀린 것

**① 문서가 지시한 오프스크린 캔버스가 이 프로젝트에서 가장 비싼 코드였다.**

"정적 배경을 별도 캔버스에 한 번 렌더해두고 매 프레임 drawImage 한 번으로 그린다."
지시대로 만들고 재봤다.

| 구현 | 프레임당 CPU | 16.7ms 초과 | 최대 |
|---|---|---|---|
| 패스 2 (오프스크린 없음) | 0.0249ms | 1회 | 61.3ms |
| **오프스크린 캔버스 blit** | **1.0307ms** | **18회** | **648.4ms** |
| ImageBitmap 으로 blit | 1.0270ms | 18회 | 645.9ms |
| **Path2D 지오메트리 캐시** | **0.0221ms** | **0회** | 10.1ms |

**41배 느려졌고, 3분에 18번씩 0.6초짜리 스톨이 났다.**
스파이크가 ~600프레임마다 규칙적으로 찍히는 걸 보고 주기적 동기화를 의심했다.
캔버스↔캔버스 전송이 범인이다. `ImageBitmap` 으로 바꿔도 똑같았다 — 전송 경로 자체의 문제다.

**지시를 그대로 따랐으면 성능 패스가 성능을 41배 악화시키고 끝났을 것이다.**

**② 힙 톱니를 게임 탓으로 돌릴 뻔했다.**

루프 안 문자열 조립을 전부 제거했는데 톱니가 972KB → 1002KB로 **안 줄었다.**
게임을 더 파기 전에 대조군을 만들었다 — rAF 체인을 끊어 게임 루프를 완전히 정지시키고
클록만 10800번 돌렸다. **게임이 하나도 안 도는데 톱니 718.9KB.**

톱니의 대부분은 브라우저와 하네스 몫이다 (`performance.memory` 읽기 자체가 객체를 만든다).
이 환경에서 "톱니 진폭 절반 이하"는 **판정 불가능한 지표**다. 그렇게 보고한다.

**③ 발판 렌더 루프에 유령 발판 버그가 있었다.**

성능을 보다가 찾았다. 렌더가 `0..platMade` 를 전부 순회하는데 이 범위는 계속 자란다
(3분이면 271칸). 그런데 발판은 **64칸 링버퍼**다.
`platYAt(i) = _platY[i % 64]` 이므로 65번째 발판이 생긴 순간부터
인덱스 0~(platMade−64)는 **재활용된 슬롯을 읽어 엉뚱한 위치에 발판을 그린다.**

30초 플레이(발판 ~50개)에서는 절대 안 보인다. 3분 플레이에서 터진다.
**성능 패스가 없었으면 D-2 영상 촬영 때 처음 봤을 버그다.**

### 어떻게 교정했나

**①** 오프스크린 캔버스를 버리고 **Path2D 로 정적 지오메트리를 캐시**했다.
문서의 목적은 "정적인 것을 매 프레임 다시 계산하지 않는다"이고,
Path2D 는 그 목적을 55배 싸게 달성한다. 지오메트리는 한 번만 만들어지고
매 프레임에는 래스터화만 일어난다. 캔버스 간 전송이 없다.
논리 해상도가 540×960 고정이라 경로는 화면 크기와도 무관하다 — 생성자에서 딱 한 번 만든다.

**③** 렌더 순회를 보이는 구간으로 좁혔다 — `platIdx−8 … platIdx+LOOKAHEAD`.
링버퍼 크기 64 안에 확실히 들어간다. O(n) 증가도 같이 사라졌다.

**추가로 한 것**

### AI가 틀린 것

**① 문서의 핵심 문장이 만들어진 게임에서 작동하지 않았다.**

문서는 "정확히 겨누려면 오래 차지해야 하는데, 차지하는 동안 물이 올라온다.
이 한 줄이 게임 전체다"라고 못박았다. 재봤다.

```
플레이어 상승 속도  ≈ 333px/s  (도약 200px ÷ 0.6초)
물 상승 속도        =  22px/s  (문서 고정값)
30초 후 수면까지    ≈ 8,950px  ≈ 화면 9장 아래
```

**칠 줄 아는 사람에게 물은 영원히 보이지 않는다.** 게임 전체라던 긴장이 존재하지 않았다.
문서 수치를 그대로 구현했고, 그래서 문서가 의도한 게임이 되지 않았다.

**② 이동 발판을 도착 시점에 판정하면서 미래를 보여주지 않았다.**

봇이 한 번도 착지하지 못했다. 발판이 도약하는 동안 최대 26px 움직이는데
착지 허용폭은 20px다. 사람도 봇도 예측할 방법이 없으면 그건 불공정한 설계다.

**③ 도달 불가능한 구간을 생성하고 있었다 — 두 번, 서로 다른 이유로.**

- 상한: 간격 상한을 415로 뒀는데, 플레이어는 발판 중심에서 최대 23px 아래에 붙는다.
  다음 간격이 438px이 되어 최대 도약 420px로는 못 넘는다
- 하한: **문서의 "차지 0% → 90px"는 도달할 수 없는 값이다.**
  최소 차지 80ms가 강제되므로 실제 최소 도약은 `90 + 330×(80/900) = 119px`다.
  간격 하한을 100으로 뒀더니 92px 간격이 생성됐고, 봇이 매번 29px 오버슛하며 죽었다.
  **문서의 두 수치(90px / 80ms)가 서로 모순이었고, 그걸 그대로 옮겨 적었다.**

**④ 부서지는 발판 뒤에 먼 간격을 붙였다.**
390px 도약은 818ms 차지를 요구하는데 발판은 700ms 만에 무너진다. 어떻게 눌러도 못 넘는다.

**⑤ 오프라인 청크 생성기의 씨앗을 `profile.length` 로 잡았다.**
PRECISE/ERRATIC(둘 다 7자), RECKLESS/BALANCED(둘 다 8자)가 같은 씨앗을 공유해

### 어떻게 교정했나

제스처 문맥이 이미 끝난 뒤라 **아무 소리도 안 난다.**

같은 패턴으로 갈 뻔했는데, 여기만 예외여야 한다.

`pointerdown` 핸들러 안에서 직접 부른다. 게임 상태는 여전히 건드리지 않는다 —

- `unlock()` 은 `pointerdown` 핸들러 첫 줄에서 부른다

- 전화 수신 등으로 다시 `suspended` 로 돌아가는 경우를 `onstatechange` 에서 되살린다
- 매 재생마다 만드는 일회용 오실레이터는 `ended` 에서 `disconnect` 한다.

### AI가 틀린 것

**1. 충돌을 목표 레인으로 판정했다. — 이 장르 교체에서 가장 컸던 버그.**

결과: **스와이프하는 순간 아직 원래 레인에 서 있는데 목적지의 장애물에 맞았다.**

`worldX` 에서 실제 위치를 되계산하는 `effLane()` 로 고쳤다.

    3분 봇 성적   고치기 전 81m / 19사망  →  고친 뒤 2175m / 1사망

### 어떻게 교정했나 — 디렉터 지표

봇 다섯을 성향별로 만들어 90초씩 돌렸더니 **다섯 다 BALANCED 아니면 ERRATIC** 으로만
판정됐다. 디렉터가 고장 났다고 보고 뜯어봤더니, 고장 난 것은 판정이 아니라 지표였다.

**(a) `reactionMs` 의 정규화 분모가 도달 불가능했다.**
분모가 `ROW_SPACING × 4` = 960 이었는데 실제 회피 입력은 z 100~180 에서 나온다.
전원이 0.82~0.90 에 몰렸고, `TH_REACT_FAST = 0.40` 은 z > 576 — 두 행 반 앞 —
을 요구했다. **PRECISE 는 구조적으로 절대 판정될 수 없었다.**

거리로 고쳤다가 다시 틀렸다. 속도가 420→760 으로 오르는 동안 똑같이 플레이해도
지표가 0.60→0.27 로 흘러내렸다. 실력이 아니라 경과 시간을 재고 있었다.
**시간으로 정규화**해서 고쳤다 — `1 − (z / 속도) / 0.8초`.

또, 표본을 "아무 레인에나 장애물이 있는 행"에서 잡고 있었다. 그러면 코인을 쫓느라
옆으로 옮긴 것까지 회피로 세어진다. **내가 서 있는 레인이 막혀 있을 때** 누른 것만 회피다.

**(b) `nearMiss` 가 플레이어가 아니라 트랙 밀도를 재고 있었다.**
빈 레인에 가만히 서 있어도 옆 레인이 막혀 있으면 아슬아슬로 집계됐다.
행당 장애물이 1.46개라 이 조건은 거의 매 행 켜졌고, 봇 넷이 전부 0.50~0.70 에
뭉쳤다. RECKLESS(`near > 0.45`)와 PRECISE(`near < 0.45`)가 **플레이어가 아니라
트랙 밀도로 갈리고 있었다.**

아슬아슬을 다시 정의했다 — (1) 자세의 **가장자리**로 넘었거나(정점에 맞췄으면 실력이다.
너무 이른 것도 너무 늦은 것만큼 위험하므로 양쪽 끝을 본다), (2) 행을 만나기 직전
16프레임 안에 그 레인으로 **뛰어들었거나**. 점수는 그대로 주고 집계만 분리했다.

**(c) `greed` 의 분모가 구조적으로 부풀어 있었다.**
세 레인의 코인을 전부 분모에 넣고 있었다. 한 몸으로 두 레인을 밟을 수 없으므로
완벽하게 욕심을 부려도 0.5 를 못 넘는다. `TH_GREED_HIGH = 0.65` 인 RECKLESS 는
**설계상 도달 불가능**했다. 게다가 분자는 지나간 행에서, 분모는 14행 앞 생성 시점에서
세고 있어 둘이 서로 다른 구간을 가리켰다.

여기서 두 번 더 틀렸다.
- "먹은 코인 / 코인이 있던 행"으로 바꿨더니, 디렉터가 중앙에 코인을 놓는 순간
  **중앙만 지키던 겁쟁이 봇의 greed 가 0.17 → 0.52 로 뛰어 도박꾼으로 분류됐다.**
  디렉터가 만든 세계가 지표를 오염시킨 것이다.
- "레인을 옮긴 지 0.5초 안에 먹었는가"로 바꿨더니, 코인을 보고 **일찍** 옮기는
  도박꾼 봇일수록 창을 벗어나 greed 가 0.04 로 내려앉았다. 정반대가 됐다.

남은 것은 위치였다. 안전한 기본값은 중앙이고, **바깥 레인의 코인을 챙기려면 반드시
그 기본값을 버려야 한다.** 분모·분자가 같은 레버의 영향을 받으므로 비율은 디렉터가
아니라 플레이어를 가리킨다. 이걸로 확정했다.

**(d) ERRATIC 을 PRECISE 보다 먼저 본다.**
문서의 나열 순서는 PRECISE 가 앞이지만, 반응이 들쭉날쭉한 사람은 평균이 아무리
빨라도 초심자다. 뒤에 두면 "가끔 아주 빠른 초심자"가 전부 장인으로 판정되고,
정작 손에 익을 시간을 줘야 할 사람에게 압력을 더하게 된다.

여기에 피격률 축을 더했다. 문서의 축은 `reactionStdev` 하나였는데, 재 보니
**초심자일수록 자주 죽고, 죽으면 지표 윈도가 리셋돼서 편차가 오히려 작아진다**
(초심자 봇 sd 0.23 < 겁쟁이 봇 sd 0.34). 편차만으로는 잡으려는 사람을 구조적으로
놓친다. 자주 부딪히는 것은 리셋에 지워지지 않는 신호다.
다만 이 축은 봇으로 발동시키지 못했다 — 봇들이 물에는 잠겨도 장애물에는 거의
안 부딪힌다. **측정으로 확인되지 않은 축이라는 것을 여기 남긴다.**

**(e) 임계값을 문서 값에서 관측 분포로 바꿨다.**
문서에서 받은 여섯 개(0.55 / 0.35 / 0.65 / 0.40 / 0.45 / 0.22)는 옛 장르의 축에
붙어 있던 숫자다. 지표를 고친 뒤 원형 봇 다섯을 각각 3분 돌려 **판정 시점의**
지표 벡터를 전부 모으고(표본 192개) 그 분포에서 다시 골랐다.

| 봇 | lane | greed | react | sd | near |
|---|---|---|---|---|---|
| 겁쟁이 | 0.71 | 0.38 | 0.65 | 0.24 | 0.27 |
| 도박꾼 | 0.50 | 0.40 | 0.36 | 0.37 | 0.22 |
| 장인 | 0.77 | 0.19 | 0.29 | 0.28 | 0.13 |
| 초심자 | 0.73 | 0.23 | 0.21 | 0.18 | 0.20 |
| 보통 | 0.55 | 0.44 | 0.44 | 0.25 | 0.21 |

`TH_LANE_HIGH` 는 0.85 로 뒀다가 아무도 도달하지 못해 0.68 로 내렸다.
트랙에 기둥이 섞여 있는 한 중앙만 지키려 해도 우회가 강제된다.

**(f) 레버가 자기 판정을 무너뜨리는 진동이 있었다.**
SAFE 정책은 중앙에 장애물을 몰아 겁쟁이를 밖으로 밀어낸다. 그런데 밀려나는 순간
중앙 체류율이 떨어져 더 이상 겁쟁이로 분류되지 않고, 정책이 풀리면 다시 중앙으로
돌아가 또 겁쟁이가 된다. ±0.05 히스테리시스로는 이 진동을 못 막는다.
**판정을 바꾼 뒤 구간 3개는 유지**하도록 했다. 정책이 효과를 낼 시간을 주고 나서
다시 판정한다.

### 어떻게 교정했나 — 측정 도구 자체

**봇이 무능하면 난이도 판단 전체가 틀린다.** 이번에도 측정 도구가 세 번 틀렸다.

1. 리드타임 없이 장애물 위에서 눌러 점프가 끝나기 전에 행을 만났다
2. 레인을 옮긴 뒤 `return` 해버려 옮긴 레인의 낮은 벽에 12번 연속으로 박았다
3. `precise` 봇을 "늦게 누르는 봇"으로 짰다. **정반대였다** — `reactionMs` 는
   늦게 누를수록 큰 값이고 PRECISE 판정은 그게 작아야 한다. 봇의 성향 정의가
   지표의 방향과 어긋나 있으면 디렉터를 검증할 수 없다

그리고 더 근본적인 것 하나. 처음엔 봇 하나에 -0.4 중앙 가중치, -0.6 코인 가중치
같은 **미세한 편향**을 얹어 다섯 성향을 만들었다. 판정 시점 분포를 재 보니 다섯의
중앙값이 lane 0.57~0.60, greed 0.33~0.40, near 0.17~0.25 로 전부 겹쳤다.
임계값을 어디에 두든 분리될 수 없는 분포였다. **측정 도구가 재려는 공간을 못 덮고
있었던 것이다.** 미세 편향이 아니라 원형(archetype)으로 다시 짰다 — 겁쟁이는
중앙에서 아예 나가지 않고, 도박꾼은 넘어야 하는 레인이라도 코인이 있으면 간다.

`precise` 의 이동 임계값을 300 으로 올렸더니 90초에 12번 죽었다. 이건 목표가 아니라
**최소 여유**라서, 크게 잡으면 늦게 나타난 행에는 아예 못 옮긴다. 장인다움은 늦게
못 움직이는 게 아니라 **더 멀리 보는 것**이라 lookahead 로 줬다.

근거는 아래 스파이크 조사다 — 비용은 폴리곤 수가 아니라 **채우는 면적**에 비례한다.

**다만 3분 측정에서 16.7ms를 넘긴 프레임이 23회 나왔다. 그냥 넘기지 않고 좁혔다.**

| 조건 | 평균 | 16.7ms 초과 | 최대 |
|---|---|---|---|
| 전체 | 0.408ms | **23회** | 191.7ms |

| `--off=오디오` | 0.432ms | 23회 | 215.2ms |

읽어낸 것:

- 대조군이 0회이므로 **환경 탓이 아니라 우리 코드다.** (패스 3에서 힙 톱니를 하네스

- 오디오·디렉터를 꺼도 그대로, **렌더를 끄면 0회.** 전부 `renderer.draw` 안이다
- 픽셀을 1/4로 줄이면 스파이크 크기가 **약 1/4로 줄지만 발생 프레임 번호는
  403, 964, 1515… 로 완전히 동일하다.** 즉 JS 로직이 아니라 **래스터 비용**이고,
  게임이 결정론적이라 언제 나올지도 정해져 있다
- 스파이크 프레임의 게임 상태는 23건 중 22건이 RUN 이다. 드래프트·결과 화면 같은
  전면 오버레이 탓이 아니다
- 나머지 프레임은 사실상 공짜다 — **p50 0.0ms, p99 0.3ms.** 10800프레임 중 23프레임의 문제다

**결론을 여기서 멈춘다.** 헤드리스 크로미움은 소프트웨어 래스터라이저를 쓴다.
GPU 합성이 도는 실기기에서 같은 일이 일어나는지는 **이 하네스로 알 수 없다.**
이것이 정확히 게이트 #2 가 "사람이 Performance 탭으로 재야 한다"고 못 박아 둔
영역이다. 추측으로 고치지 않는다 — DPR 상한 2 는 이미 걸려 있고(스파이크가 면적에
비례하므로 이게 곧 상한이다), 실기기 측정 전까지 **남은 최대 리스크로 표시해 둔다.**

#4 는 처음에 실패로 나왔다. 원인을 파 보니 게임이 아니라 **하네스의 합성 클록**이었다.
delta 가 부동소수점 때문에 `SIM_DT` 보다 1e-15 작을 때가 있어 그 프레임은 시뮬
스텝을 건너뛰고 다음 프레임에 두 번 돈다. 의도된 동작이고 시간당 스텝 수는 정확하다
(게이트 #1 오차 0.00%가 그 증거다). 게이트가 "큐 소비"와 "화면 반영"을 한 덩어리로
재고 있었던 것이라 둘을 분리했다. **게이트를 통과시키려고 느슨하게 한 것이 아니라,
재려던 것을 제대로 재게 고친 것이다.**

### 남은 부채

- **16.7ms 초과 23회의 실기기 재현 여부.** 헤드리스에서는 래스터 비용으로 좁혔지만
  GPU 합성 기기에서도 나오는지는 사람이 재야 한다. **남은 최대 리스크다**
- **피격률 축(`TH_HIT_HIGH`)은 측정으로 확인되지 않았다.** 봇이 장애물에 거의
  안 부딪혀 발동시키지 못했다. 사람 플레이로 확인해야 한다
- 디렉터 지표는 레버의 영향을 받는다. 구간 3개 유지로 진동은 잡았지만 완전히
  독립적이지는 않다. 이건 적응형 디렉터의 본질적 성질이지 결함은 아니다
- 초심자 봇이 실제로는 초심자만큼 못하지 않는다. 리드타임을 0.15~2.0배로 흔들어도
  거의 안 부딪힌다 — 트랙이 그만큼 관대하다는 뜻이기도 하다
- 드래프트 제시 분포는 성향별로 2종으로만 갈렸다. 5종 전부가 서로 다른 분포를
  내는지는 확인하지 못했다
- `data/*.json` 은 여전히 **오프라인 자리표시자**다. D-3 에 실제 LLM 으로 다시
  구워야 하고, 그 전까지 "LLM이 만든 350청크"는 사실이 아니다
