## 2026-08-01 (D-9) — 패스 0 · 배포 캐너리 — 지휘: A

### 내린 지시

「전문가 빌드 프롬프트 세트」의 프롬프트 0을 그대로 집행했다.
지시의 핵심은 만들라는 것보다 **만들지 말라는 것**이었다 —
"게임을 만들지 마라. 기능을 넣지 마라. 이 파일 3개 외에 아무것도 만들지 마라."

만든 것은 3개뿐이다.

- `index.html` — `<h1>RISING</h1>` 과 `<p>D-9 canary</p>` 두 줄. 그 외 아무 내용 없음
- `docs/ai-log.md` — 이 파일
- `README.md` — 팀 롤(A=빌드 / B=검증), 저장소 구조, URL 자리

`index.html`에 강제한 조건:

- `viewport` 에 `viewport-fit=cover, user-scalable=no`
- body 에 `touch-action: manipulation`, `user-select: none`,
  `-webkit-tap-highlight-color: transparent`, `margin: 0`
- 배경 `#12242E`, 글자 `#F4F7F5`

이 4줄은 캐너리에 넣을 이유가 없어 보이지만 넣었다.
모바일 제스처 차단(게이트 #5)은 나중에 붙이면 "왜 확대가 되지" 를 디버깅하게 된다.
지금 넣으면 0초, 나중에 넣으면 30분이다.

### AI가 틀린 것

**저장소가 완전히 비어 있다는 사실을 확인하기 전에 계획을 세울 뻔했다.**
커밋 0개 · 브랜치 0개였다. 기본 브랜치조차 없었다.
이건 계획에 실제로 영향을 준다 — GitHub Pages 는 브랜치에서 서빙되는데,
첫 푸시된 브랜치가 기본 브랜치가 되어버린다.
작업용 브랜치(`claude/document-work-icemu4`)가 기본 브랜치가 되면
문서가 말한 "성역 URL" 이 throwaway 브랜치에 묶인다.

확인 후 사람에게 물어 `main` 을 함께 만들기로 확정했다.
**묻지 않고 진행했으면 URL 이 작업 브랜치에 묶인 채로 9일을 갔다.**

### 어떻게 교정했나

동일 내용을 `main` 과 작업 브랜치 양쪽에 푸시했다.
Pages 는 `main / (root)` 에서 서빙한다. 작업 브랜치가 사라져도 URL 은 산다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

| 게이트 | 항목 | 상태 | 값 |
|---|---|---|---|
| #8 | 콘솔 청결 | 자동 측정 대기 | 패스 1 이후 헤드리스로 측정 |
| #9 | 링크 접근성 | **사람 확인 필요** | Pages 활성화 후 B가 폰 LTE로 |

**이 시점에 통과했다고 말할 수 있는 게이트는 하나도 없다.**
Pages Source 스위치는 GitHub 설정 UI 에서만 켤 수 있고 (이 세션의 GitHub 도구에 Pages API 가 없다),
폰 LTE 접속은 사람만 할 수 있다.

문서가 정의한 D-9 하드컷은 "캐너리 URL 이 B의 폰 LTE 로 열림" 이다.
**저장소 상태로는 준비가 끝났지만, 하드컷 자체는 아직 통과하지 않았다.**
스위치 하나 + 폰 하나가 남아 있다. 이 둘이 D-9 안에 끝나야 한다.

### 남은 부채

- **git 태그를 원격에 올리지 못한다** — 커밋 직후 발견했다.
  이 세션의 git 프록시는 `refs/heads/*` 푸시는 통과시키지만 `refs/tags/*` 는 403으로 거부한다.
  4회 재시도 모두 동일한 403이므로 일시적 오류가 아니라 정책이다.
  **태그 대신 커밋 SHA를 롤백 지점으로 README 에 표로 남긴다.**
  사람이 로컬에서 `git tag <이름> <SHA> && git push origin --tags` 로 한 번에 만들 수 있다.
  태그가 롤백 지점 역할을 하는 건 변함없다 — 지금은 이름이 SHA일 뿐이다.
- **Pages Source 활성화 (사람)** — Settings → Pages → `main` / `(root)`
- **URL 을 README 최상단에 기입 (사람)** — 지금은 자리 표시자다
- **B의 폰 LTE 접속 확인 (사람)** — 이게 되어야 배포다. 와이파이는 증거가 아니다
- 공식 페이지에서 신청서 양식·팀 인원 조건 직접 확인 (사람)
- A·B 각각 최소 1커밋 — AI 커밋은 사람 커밋을 대신하지 못한다.
  2인 팀 롤 기술서의 증거는 사람의 커밋 로그다

## 2026-08-01 (D-8 작업을 D-9에 선행) — 패스 1 · 코어 루프 — 지휘: A

### 내린 지시

프롬프트 1을 그대로 집행했다. 지시의 무게중심은 게임이 아니라 **네 가지 구조**에 있었다.

1. 고정 타임스텝 + 누산기 (delta 250ms 클램프, 렌더 보간, visibilitychange 리셋)
2. 입력 큐 (핸들러는 큐에 넣기만, 프레임 시작에서 소비, `event.timeStamp` 사용)
3. 상태 기계 (전이는 한 곳에서만)
4. devicePixelRatio 는 resize 에서만

만든 파일: `index.html`, `src/config.js`, `src/main.js`, `src/game.js`.
연출·성능·난이도·색·소리는 전부 뒤 패스 몫이라 손대지 않았다.
발판 배치는 고정 패턴 8개 하드코딩, 랜덤 0.

### AI가 틀린 것

**① 문서의 「발판 두께 12」를 그대로 착지 허용폭으로 쓰면 게임이 성립하지 않는다.**

두께 12 → 반두께 6 → 허용 ±6px.
그런데 같은 문서가 정한 조준 진동 진폭은 `조준선 길이 × 0.06` 이다.
420px 최대 도약에서 진폭은 ±25.2px — **허용폭의 4배**다.
원거리 도약은 사인파를 완벽하게 읽어도 산술적으로 착지가 불가능하다.

수치를 의심하지 않고 그대로 구현했으면 "구현은 스펙대로인데 게임이 안 되는" 상태로
D-7 게임필 패스까지 갔을 것이다. 거기서 발견하면 물리 수치를 되돌려야 하고,
물리 수치는 패스 2가 보호해야 할 영역이다.

**② 첫 60Hz/120Hz 측정에서 발판 수가 49 / 51 로 갈렸다 (오차 4.08%, 목표 3% 미만).**

게임의 고정 타임스텝을 의심했다. 그런데 시뮬레이션 틱은 **1799 / 1799 로 완전히 동일**했다.
틱이 같은데 결과가 다르면 게임이 아니라 입력이 다른 것이다.
원인은 내가 만든 측정 봇이었다 — 봇이 매 렌더 프레임마다 판단해서
120Hz 회차에서 두 배 자주 폴링했고, 그만큼 반응이 빨라졌다.
**사람의 반응 속도는 주사율에 비례해서 빨라지지 않는다.** 측정 도구가 틀렸다.

멀쩡한 누산기를 "고쳤으면" 진짜 버그를 심을 뻔했다.

### 어떻게 교정했나

**①** 착지 허용폭을 `발판 반두께 + 플레이어 반지름` = **20px** 으로 정의했다.
플레이어는 점이 아니라 반지름 14의 원이므로 원의 가장자리가 발판에 걸리면 붙는 게 물리적으로 맞다.
`aimError` 도 이 값으로 정규화한다 — 디렉터의 임계값 0.4 / 0.6 이 의미를 갖는 유일한 기준이다.

수치 검산:

| 도약 거리 | 진동 진폭 (×0.06) | 허용폭 | 결과 |
|---|---|---|---|
| 90px (근거리) | ±5.4px | ±20px | 위상과 무관하게 붙는다 |
| 240px (중거리) | ±14.4px | ±20px | 대충 눌러도 붙는다 |
| 420px (원거리) | ±25.2px | ±20px | **사인파를 읽어야만 붙는다** |

문서가 의도한 "근거리는 거의 안 흔들리고, 원거리는 크게 흔들린다"가 수치로 성립한다.
완벽 착지(중심 ±12%)는 ±2.4px — 근거리에서도 타이밍이 필요하다.

**②** 봇의 판단을 화면 주사율이 아니라 **고정 60Hz 격자**에 묶고,
주입하는 `timeStamp` 도 격자 시각으로 고정했다.
이제 두 회차의 입력 스트림이 완전히 동일하므로, 차이가 나면 그건 게임 탓이다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

`tools/smoke.mjs` — Playwright + 합성 클록(rAF·performance.now 스텁) 헤드리스 하네스.
실기기 120Hz 화면이 없어도 게이트 #1 을 실제로 잴 수 있다.

| # | 항목 | 측정값 | 판정 |
|---|---|---|---|
| 1 | 60Hz vs 120Hz 속도 동일성 | 30초 후 도달 발판 **49 / 49 (오차 0.00%)**, 시뮬 틱 **1799 / 1799** | 통과 (목표 <3%) |
| 3 | 탭 전환 복귀 (30초 방치) | 복귀 후 틱 1197 / 정상 1200 (**편차 0.25%**), 누산기 잔여 16.667ms | 통과 |
| 8 | 콘솔 청결 | 에러·경고 **0개** | 통과 |
| — | 루프 왕복 | 방치 32초 → 사망 관측, 입력 1회로 재시작, 판수 2 | 통과 |

**틱 1799 / 1799 가 이 패스의 핵심 증거다.** 30초 × 60Hz = 1800 스텝이고,
어떤 주사율에서 돌려도 시뮬레이션이 정확히 같은 횟수만큼 돌았다는 뜻이다.
심사자 모니터가 60Hz인지 144Hz인지 몰라도 된다.

### 남은 부채

- 게임필이 전무하다 — 히트스톱·입력버퍼·코요테·스쿼시 전부 패스 2
- 렌더 코드가 `main.js` 안에 있다. 패스 3에서 오프스크린 배경과 함께 `render.js` 로 분리한다
- `tools/smoke.mjs` 는 프롬프트 1의 파일 목록에 없는 파일이다.
  하지만 "60Hz와 120Hz에서 오차 3% 미만"은 프롬프트 1이 스스로 요구한 완료 조건이고,
  실기기 없이 그걸 잴 유일한 방법이었다. 게임은 이 파일을 로드하지 않는다
- 실기기 확인 0회 — iPhone·Android 둘 다 아직 안 돌렸다 (게이트 #4·#5·#7)
- 물 근접·사망 연출이 없어 지금은 죽어도 밋밋하다. 패스 2·5·6에서 붙는다

## 2026-08-01 (D-7 작업을 D-9에 선행) — 패스 2 · 게임필 — 지휘: A

### 내린 지시

프롬프트 2를 순서대로 집행했다. 이 프롬프트의 핵심은 목록이 아니라 **순서**다 —
효과 크기 순으로 배열돼 있고, 시간이 모자라면 아래쪽이 잘린다.

| | 항목 | 상태 |
|---|---|---|
| ① | 히트스톱 (착지 3f / 완벽 6f / 사망 8f→0.15배속 400ms / 신기록 4f) | 완료 |
| ② | 입력 버퍼 6프레임 | 완료 |
| ③ | 코요테 5프레임 | 완료 (패스 1에서 이미 시뮬레이션에 들어가 있었다) |
| ④ | 스쿼시 & 스트레치 | 완료 |
| ⑤ | 스크린 셰이크 (3/5/12/6, 감쇠 0.85, 사망 시 회전, 물 근접 상시 미세진동) | 완료 |
| ⑥ | 이징 (UI·스쿼시 easeOutBack / 링 easeOutCubic / 조준선·물은 선형 고정) | 완료 |
| ⑦ | 진동 조준 (사인파, 진폭 = 길이×0.06, 주기 620ms) | 완료 (패스 1에서 선행) |
| ⑧ | 파티클 (6 / 12 / 20, 배열 재사용) | 완료 |
| ⑨ | 트레일 4프레임 · 카메라 리드 | 완료 |

**하나도 버리지 않았다.** ③⑦이 패스 1에 먼저 들어간 건 둘 다 착지 판정 자체에
관여하는 시뮬레이션 규칙이라, 연출 레이어로 미루면 물리를 두 번 고쳐야 했기 때문이다.

건드리지 않은 것: 고정 타임스텝 누산기, 입력 큐 구조, 상태 기계 전이 규칙, 물리 수치.
게임필은 `src/feel.js` 라는 별도 레이어에 있고, 이벤트를 받기만 한다.

### AI가 틀린 것

**① 입력 버퍼를 "누른 것만 기억"으로 만들면 짧은 탭이 무한 차지로 남는다.**

문서는 "착지 6프레임 전에 들어온 입력을 기억했다가 착지 즉시 차지를 시작한다"고만 썼다.
그대로 만들면 이런 일이 생긴다 — 도약 중에 톡 눌렀다 뗀다 → 누른 건 버퍼에 남고
뗀 건 CHARGING 상태가 아니라 버려진다 → 착지하는 순간 차지가 시작되는데
플레이어 손은 이미 화면에서 떨어져 있다 → 1200ms 오버차지 강제 발사까지 끌려간다.

**릴리스도 같이 기억해서 착지 시점에 그대로 재현**해야 한다.
플레이어가 실제로 누른 시간만큼 차지하고 즉시 발사된다.

**② 60Hz/120Hz 완벽 착지 수가 3 / 5 로 갈렸다. 첫 가설이 틀렸다.**

`frameSimBase = game.simTime` 으로 잡고 있었는데, `simTime` 은 "마지막으로 시뮬레이션된
순간"이고 누산기에는 아직 시뮬레이션되지 않은 시간이 0~16.7ms 담겨 있다.
즉 기준점이 매 프레임 누산기 잔여분만큼 뒤처져 있었고, **그 잔여분은 주사율마다 다르다.**
조준 진동 위상이 그만큼 흔들리니 완벽 착지(±2.4px)가 갈린다 — 이게 첫 가설이었다.

`frameSimBase = game.simTime + accumulator` 로 고쳤다. 논리적으로 명백히 옳은 수정이다.
**그런데 다시 재보니 3 / 5 가 그대로였다.** 가설이 원인의 전부가 아니었다.

### 어떻게 교정했나

**②의 진짜 원인**은 따로 있었다. 입력은 프레임 시작에서 소비되는데,
그 시점에 시뮬레이션이 어디까지 진행돼 있는지가 주사율마다 최대 1스텝 다르다.
같은 입력이 60Hz에서는 착지 직전(→ 입력 버퍼 경로)에, 120Hz에서는 착지 직후
(→ 직접 차지 경로)에 소비될 수 있다. 두 경로는 차지 시작 시각이 다르고,
조준 진동은 절대 시각의 함수이므로 위상이 달라진다.

**이건 입력 버퍼가 있는 모든 게임에 내재된 성질이고, 고칠 대상이 아니다.**
차이는 최대 1프레임이며, 도달 발판 수(게이트 #1의 판정 기준)에는 영향이 없다 — 45 / 45.

진동 위상을 절대 시각 대신 **차지 경과 시간**의 함수로 바꾸면 이 차이가 사라진다.
검토했고, **버렸다.** 그렇게 하면 진동 위상과 도약 거리가 둘 다 "누른 시간"만의
함수가 되어 서로 완전히 종속된다. 자유도가 2개에서 1개로 줄고,
문서가 설계한 두 축("얼마나 오래 누를까" / "진동의 어느 순간에 뗄까")이 하나로 무너진다.
**측정값을 예쁘게 만들려고 게임을 망가뜨리지 않는다.**

`frameSimBase` 수정은 그대로 두었다. 원인의 전부는 아니었지만 그 자체로 옳다.

### 무엇으로 검증했나 (품질 게이트 번호와 측정값)

| # | 항목 | 측정값 | 판정 |
|---|---|---|---|
| 1 | 60Hz vs 120Hz | 도달 발판 **45 / 45 (오차 0.00%)**, 도달 높이 9092.00 / 9099.80 (0.09%), 시뮬 틱 1655 / 1649, 완벽착지 3 / 5 | 통과 |
| — | 재현성 (사인파 실증) | 동일 입력 2회 → 최종 playerY **9092.003775 / 9092.003775 비트 동일**, 완벽착지 3 / 3 | 통과 |
| 4 | 입력 지연 (코드 레벨) | 입력 주입 → **1프레임 후** READY→CHARGING. 큐가 프레임 시작에서 소비됨을 확인 | 통과 (실기기 녹화는 사람 몫) |
| 3 | 탭 전환 복귀 | 대조군 1106 / 탭 전환 1098 (편차 **0.72%**), **히트스톱 잔여 0f, 슬로우 잔여 0f** | 통과 |
| 8 | 콘솔 청결 | 에러·경고 **0개** | 통과 |

**재현성의 playerY가 소수점 6자리까지 동일한 것이 ⑦의 증거다.**
조준 진동에 `Math.random()`이 한 톨이라도 섞였으면 이 숫자는 절대 같을 수 없다.

시뮬 틱 1655 / 1649 차이는 히트스톱 프레임 수 차이(완벽 착지 3회 vs 5회 × 6프레임)에서
그대로 나온다. 히트스톱 자체는 시뮬레이션 프레임으로 세므로 주사율과 무관하다.

### 남은 부채

- **완벽 착지 수가 주사율에 따라 3 / 45 ~ 5 / 45 범위에서 흔들린다.**
  원인은 위에 적었고 고치지 않기로 결정했다. 도달 발판 수에는 영향이 없다.
  실기기 120Hz(A 담당)에서 재확인 필요
- 렌더가 아직 `main.js` 안에 있다. 오프스크린 배경과 함께 패스 3에서 분리
- 파티클은 "고정 크기 배열 재사용" 수준이다. 정식 풀 검증과 루프 내 할당 0 확인은 패스 3
- 물 근접 경고에 `createLinearGradient` 를 쓰는데 한 번만 만들어 재사용한다.
  패스 3에서 루프 내 할당 감사 때 다시 확인할 것
- 실기기 확인 0회 — 히트스톱과 셰이크는 손으로 만져봐야 안다. iPhone·Android 필수
