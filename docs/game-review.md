## 이 평가의 성격

이 문서는 서로 독립적으로 움직인 **4인의 심사위원**이 각자 실제로 플레이한 뒤 제출한
보고서를 한 사람(통합 작성자)이 모아 교차 분석한 **합동 평가**다. 4인은 사전에 관점을
나눠 가졌다 — 심사위원1은 "냉정한 대회심사", 심사위원2는 "AI활용 전문", 심사위원3은
"캐주얼 플레이어", 심사위원4는 "차별화 중심" — 이고, 서로의 보고서를 보지 않은 채
각자 저장소를 로컬로 서빙해(`python3 -m http.server 882{1,2,3,4}`) Playwright headless
Chromium으로 **실제 클릭·키보드 입력**을 주입하며 플레이했다. 네 명 모두 빌드 단계가
없는 정적 HTML/CSS/JS 저장소를 그대로 서빙했으므로, 이 결과는 실제 배포 URL이 서빙할
코드와 동일한 코드를 대상으로 한다 — 로컬 재현과 배포본 사이에 차이가 날 이유가 없다.

합산 실측 플레이 시간은 4인 총 약 25~27분(6~7분 + 8분16초 + 5분52초 + 6분30초),
스크린샷은 4인 합산 약 269장, 콘솔/페이지 에러 계측은 4인 전원이 `page.on('console')`
/ `page.on('pageerror')`로 수행했다. **네 세션 전부에서 콘솔 에러 0건, 페이지 에러
0건**이 보고됐다 — 서로 다른 전략(직접 조작, 단일유닛 도배, 완전 유휴, 카운터 반응
봇, 다양한 전략, 절제된 혼합 구매, 즉흥 구매, 스팸 구매)과 서로 다른 실행 환경(포트
8821~8824)에서 독립적으로 얻은 결과이므로 안정성에 대한 신뢰도는 높다.

통합 작성자는 4인의 보고서 텍스트를 그대로 신뢰해 집계했으며, 그 위에서 딱 두 가지
사실관계만 저장소를 직접 열어 재확인했다 — (1) 심사위원3·4가 상반되게 해석한
`data/chunks.json`의 현재 상태, (2) 심사위원4가 지적한 "저장소에 섞인 스테일 문서"의
실존 여부(바로 이 파일, `docs/game-review.md`의 교체 전 상태). 두 건 모두 아래
본문에서 직접 확인한 근거와 함께 다룬다. 그 외의 모든 서술(스크린샷, 코드 줄 번호,
실측 초 단위 등)은 4인 각자의 원문을 그대로 따른 것이며, 통합 작성자가 재검증하지
않았다 — 자세한 한계는 "이 평가의 한계" 절에 명시한다.

## AI 활용 종합 평가

이 항목은 대회 성격상 가장 중요하게 다뤄야 할 축이며, "AI활용 전문" 관점의
위원2가 가장 엄밀한 방법으로 검증했다.

**적이 플레이어 행동에 실시간으로 반응한다는 것은 통제된 실험으로 입증됐다.**
위원2는 궁수(`3`) 단일유닛만 반복 구매하는 순수 단일변수 세션(Run 2)에서
`director.js`의 `levers.mix` 배열을 5회 이상 폴링해, 궁수의 카운터 유닛인 기병의
가중치가 반복적으로 20~25대까지 치솟고 다른 유닛은 0.5~4대에 머무는 것을
확인했다(`iter250`~`iter700` 전 구간 재현). 이는 `config.js`의
`COUNTER[U_CAV][U_ARCHER]=2.5` 테이블과 정확히 대응한다. 같은 위원의 Run 1(다양한
전략)에서는 디렉터가 매긴 플레이어 프로파일이 "물량형"→"돌격형"으로 실시간
전환되는 것도 확인했다. 이 발견은 다른 세 위원의 관찰과도 정합적이다 — 위원1은
완전 유휴/도배/카운터봇 3가지 플레이 스타일에 각각 다른 프로파일 라벨(수비형/
물량형/경제형)이 정확히 붙는 것을, 위원3·4는 드래프트 카드의 "디렉터가 이 셋을
고른 이유" 문구가 서로 다른 세션에서 같은 플레이 패턴(스팸)에 같은 문구("숫자로만
밀고 있다 — 한 방을 준다")로 반복 등장하는 것을 각각 독립적으로 확인했다. **네 개의
독립 세션이 같은 결론에 수렴한다**: 판정은 연출이 아니라 매 순간 재계산되는 실제
로직이다.

**판단 근거가 화면에 노출되고, 그 노출이 사실과 일치한다.** 디렉터 뷰(우상단 `AI`
토글)는 4인 전원이 실제로 켜서 확인했다. 5개 지표 막대(공격성·비축·경제·물량·상성
우위)와 "보는 것"(플레이어 실제 구성)·"지시"(다음 웨이브 구성) 아이콘 행이
나란히 뜨고, 위원2는 도배 전략에서 "보는 것"이 궁수 칸만, "지시"가 기병 칸만
채워지는 것을 직접 캡처했다. 위원3은 사령관 고정 배지("물량형")와 디렉터 실시간
판정("경제형")이 서로 다르게 찍히는 것을 확인해 — 값이 다르다는 사실 자체가 후자가
독립적으로 계산되고 있다는 증거임을 지적했다.

**계층 구조와 그 한계.** 이 게임은 스스로 두 계층으로 설계돼 있다 —
계층1(런타임 디렉터, `src/director.js`)과 계층2(오프라인 LLM 베이크,
`data/*.json` + `tools/bake.js`). 네 위원의 검증은 전부 계층1에 집중돼 있고,
계층1은 위 근거들로 강하게 뒷받침된다. 계층2에 대해서는 위원3과 위원4가 같은
파일(`data/chunks.json`)을 보고 상반된 결론을 냈다 — 위원3은 "README가 요구한
LLM 베이크가 미완료"라고, 위원4는 "적어도 README가 경고한 `offline-placeholder`
상태는 아니다"라고 판단했다. **통합 작성자가 저장소를 직접 열어 확인한 결과는
다음과 같다**:

```
data/chunks.json: "generator":"authored:claude", "provenance":{"authored":350,"llm":0,...}
data/lines.json:  "generator":"authored:claude"
```

즉 두 위원 모두 부분적으로 맞다. `offline-placeholder`(README가 경고한 미완료
상태)는 이미 벗어났다는 점에서 위원4가 맞고, 그러나 `provenance.llm`이 0이라는
점에서 — README가 D-3 체크리스트에 명시한 "`export OPENAI_API_KEY=...` →
`node tools/bake.js`"라는 **실제 API 호출 경로를 거친 콘텐츠는 여전히 0개**라는
점에서 위원3이 맞다. 현재 상태는 코딩 에이전트(Claude)가 350개 웨이브 문구를
직접 손으로 저술한 것("저술 350 / 총 350")이며, 이는 "LLM이 만든 콘텐츠"라는
주장 자체는 문자 그대로 거짓이 아니지만, README가 스스로 지시한 검증 파이프라인
(`node tools/bake.js` → `node tools/verify-chunks.js`)은 아직 한 번도 통과하지
않은 상태로 보인다. 대회가 "AI 활용"을 심사한다면 이 계층2의 미완료 상태는
가볍게 넘길 사안이 아니다.

**종합 결론**: 플레이어가 실제로 만나는 AI(계층1 런타임 디렉터)는 네 개의 독립
세션에서 일관되게 "반응하는 판단"으로 확인됐다 — 이 대회의 핵심 심사 기준에서
상위권으로 평가할 근거가 충분하다. 다만 계층2(오프라인 LLM 베이크)는 README
자신이 정한 완료 기준을 아직 통과하지 못했고, 이는 대회의 "AI로 무엇을 만들었는가"
라는 질문에 직결되므로 제출 전 반드시 정리해야 한다.

## 가장 좋은 것 (종합)

콘솔 에러 0건 · 페이지 에러 0건이 4인 합산 25분 이상, 269장의 스크린샷, 서로 다른
8가지 플레이 스타일에서 예외 없이 확인됐다 — 이 자체가 안정성에 대한 강한 신호이며,
아래 세 가지 강점이 그 위에서 성립한다.

1. **디렉터의 판단 근거가 화면에서 검증 가능하다.** 4인 전원이 "가장 좋은 것" 1순위
   또는 2순위로 이 항목을 꼽았다. 디렉터 뷰의 5개 지표 막대와 "보는 것/지시" 대조,
   드래프트 카드의 "디렉터가 이 셋을 고른 이유" 문구가 그 순간의 실제 플레이 패턴과
   반복적으로 일치했다(위원1·3·4가 독립 세션에서 동일 현상 재현, 위원2는 이를
   `director.levers.mix` 수치 폴링으로 정량 입증). 연출이 아니라 판단이라는 것을
   네 명이 각자 다른 방법으로 증명했다.

2. **상성·시대진화가 숫자가 아니라 사건으로 나타난다.** 궁수 단일 도배(진화 없음)는
   반복 패배했고, 카운터에 반응하는 혼합/진화 전략은 승리했다(위원1·2가 대조
   실험으로 확인). 3번째 사령관("금고")과의 전투에서 거의 이긴 판이 10초 안에
   전멸로 뒤집히는 것을 위원1과 위원3이 서로 다른 세션에서 각각 관찰했다 — "너는
   지금 쓰고, 나는 나중에 쏟는다"는 소개 문구가 실제 게임 사건이 됐다. 시대 진화도
   이름·능력·팔레트를 실제로 갈아엎고(돌도끼병→청동검사→강철기사), 원정 안에서
   전투 간 승계되는 것이 위원2·4에 의해 실측 확인됐다.

3. **에셋 0개 제약이 핑계가 아니라 스타일로 성립한다.** 이미지·오디오 파일 없이
   Canvas 도형만으로 5개 시대(돌기→기계) 전부가 확연히 다른 인상을 준다는 것을
   4인 전원이 독립적으로 지적했다. 밝기=진영, 색상=병종, 위협색(분홍/빨강)은
   적 예고 전용이라는 시각 문법이 269장의 스크린샷 전체에서 예외 없이 지켜졌다.

## 가장 나쁜 것 (종합) — 공통 지적 우선

### 최우선 — 2인 이상 명시적 지적 + 4인 전원 간접 확인

**1. 후반 콘텐츠(사령관4·5, 보스 「심연」, 최강병기 「거신」)를 아무도 확인하지
못했다.** 4인 합산 25분 이상, 원정 완주 시도 총 9회 이상(실패 포함)에도 불구하고
**단 한 명도** 5번째 사령관·보스·최강병기에 도달하지 못했다(위원1: 4회 시도 전부
사령관3에서 종료, 위원2: 5번째 전투를 빠르게 훑고 지나가 확증 실패, 위원3: 최고
도달 사령관3, 위원4: 4번째 사령관 패배 후 리셋). 위원3(#1)과 위원4(#3)는 이를
명시적으로 "가장 나쁜 것"으로 꼽으며 "짧은 심사 세션에서는 후반 콘텐츠가 아예
노출되지 않을 위험"을 지적했다. README가 강조하는 차별점(보스·최강병기)이 실제
심사 시간 안에 보일지 불확실하다는 것은 코드 존재 여부와 별개의, 페이싱 설계 문제다.

**2. 첫 30초~첫 전투에 "내가 질 수도 있다"는 신호가 없다.** 위원1(#2)과 위원2(#3)가
명시적으로 지적했고, 위원3·4는 첫 30초 항목 점수 감점 근거로 같은 관찰을 명시했다 —
사실상 4인 전원이 동일한 현상을 확인했다. 능동적으로 플레이한 세션 대부분에서 첫
전투 중 내 기지 체력 손실이 사실상 0이었다("이기라고 있는" 난이도). 이 항목은
배점의 20%(20/100)를 차지하는 만큼, 초반 텐션 부재는 총점에 직결되는 리스크다.

### 차상위 — 단일 지적이나 구체적·재현 가능·치명적

**3. 디렉터 뷰 패널이 플레이어 기지 스프라이트를 가린다.** 위원1이 `src/render.js`
6210행 `drawDirectorView(x=16, y=96, w=250, h=288)`를 특정해 지적했다 — 이 좌표가
정확히 플레이어 기지 위치와 겹쳐, 4장의 스크린샷(52·58·62·63)에서 기지 스프라이트가
아예 보이지 않고 숫자 HP만 남는다. README가 제출 영상에 반드시 담으라고 명시한 바로
그 화면이, 심사에서 가장 중요한 "내 기지가 얼마나 위험한가"를 가리는 셈이다. 단일
위원 지적이지만 코드 줄·좌표·스크린샷 4장으로 재현 가능하며, 이 게임의 핵심
셀링포인트(디렉터 뷰)를 직접 훼손한다는 점에서 우선순위를 높였다.

**4. `data/*.json`이 README 자신의 D-3 체크리스트를 문자 그대로 통과하지 못했다.**
위원3이 지적했고(위원4는 반대로 해석), 통합 작성자가 직접 재확인했다("AI 활용
종합 평가" 절 참조) — 현재 `generator: "authored:claude"`, `provenance.llm: 0`으로,
`offline-placeholder`는 벗어났으나 README가 지시한 실제 API 베이크 경로는 아직
한 번도 실행되지 않았다.

**5. 신규 세션의 "첫" 별자리가 사실상 고정돼 있다.** 위원2가 `main.js` 전수
검색으로 `game.setZodiacSeed()`를 호출하는 실제 코드 경로가 없음을 확인했다(테스트
하네스 전용 API로만 존재, `config.js` 309행 주석이 이를 인정). 즉 `zodiacSeed`는
항상 기본값 0이라, 모든 신규 플레이어의 첫 전투는 항상 같은 별자리("전갈·독아")로
시작한다. "판마다 다시 시작할 때마다 바뀐다"는 README 주장은 세션 내에서는 맞지만,
서로 다른 사람들의 "첫 판"끼리는 다르지 않다.

**6. 승리·패배 배너가 같은 색으로 겹친다.** 위원2가 지적 — 전투 종료 직후 뜨는
배너("전투를 이겼다"/"원정이 끝났다")가 승패와 무관하게 동일한 톤으로 그려진다
(완전히 떠오른 결과 카드는 코드상 승=금색/익사=빨강/패배=중립흰색으로 분리돼
있으나, 그 직전 배너 단계엔 색 구분이 없다). 승패가 갈리는 가장 중요한 순간에
즉각적인 색 구분이 없다는 것은 "성공과 실패의 감촉이 다른가" 항목에서 손해다.

**7. 핵심 셀링포인트("상성이 승패를 가른다")가 개발팀 자체 실측으로 목표
미달임이 문서에 남아 있다.** 위원4가 `README.md` 192-219행과
`docs/auto-improve-log.md` 228-231행을 근거로 지적했다 — 상성-도배 격차가
목표(≥40%p)에 미달(−18%p → +3%p에서 정체, 6종 전체 기준 여전히 음수)이라고
개발팀 스스로 문서화했다. 위 "종합 점수표"에서 설명했듯 이는 다른 3인의 블랙박스
실측(카운터가 도배를 이긴다)과 모순되지 않는 별개의, 더 엄격한 기준에서의 미달이며
가볍게 볼 사안은 아니다.

### 경미 — 부수적

**8. 인트로/브리핑 화면 정보 밀도 과다.** 위원3이 명시적으로 지적했고, 위원1·4도
같은 화면(상성 육각다이어그램+3대 규칙+10칸 단축키표가 한 화면에 동시 노출)의
정보량이 많다는 점을 첫 30초 서술에서 함께 언급했다.

**9. 저장소에 스테일 문서가 섞여 있었다.** 위원4가 `docs/game-review.md`(교체
전) 전체가 "차오른다"가 아니라 이전 3레인 러너 장르를 채점한 결과임을 지적했다.
통합 작성자가 직접 열어 확인한 결과 사실이었다(교체 전 파일 180줄, "코인의
70~97%가 바깥 레인에 놓인다" 등 완전히 다른 게임의 서술) — **본 보고서가 그 파일
자체를 이 내용으로 교체하며 해결한다.**

### 해석이 갈린 지점 — 하나 덧붙임

3번째 사령관("금고")과의 전투에서 벌어지는 급격한 체력 역전(수십 초 이내 90%대에서
0으로)을 위원1은 "회복 불가능한 절벽형 붕괴"로 부정 평가했고, 위원3은 같은 현상을
"사령관 개성이 사건으로 구현된 훌륭한 예"로 긍정 평가했다. 동일한 게임 이벤트에
대한 정반대 해석이다 — 개발팀이 의도한 "위기감 있는 반전"과 "만회 불가능한 불공정함"
사이의 줄타기이므로, 최소한의 완충(예: 붕괴 초입에 더 강한 경고, 짧은 재정비 여유)을
검토할 가치가 있다.

## 최종 판정: **조건부**

4인 중 3인(위원1·3·4)이 독립적으로 "조건부"를, 1인(위원2)이 "제출 가능"을 냈다.
다수결이 아니라 근거를 따져 같은 결론에 도달한다.

핵심 루프와 AI 디렉터는 실제로 작동한다 — 4개의 독립 세션 모두 콘솔/페이지 에러
0건이었고, 위원2의 통제된 단일변수 실험(궁수 도배 → 기병 카운터 가중치 20~25배
상승)이 "적이 내 행동에 반응한다"는 핵심 주장을 정량적으로 입증했다. 이것만으로는
"제출 가능"이 맞는 결론이다.

그러나 이 결론을 뒤집는 것이 아니라 **유보 조건을 다는** 세 가지가 독립적으로 쌓여
있다.

1. **후반 콘텐츠 도달 실패가 우연이 아니다.** 4인 전원, 9회 이상의 진지한 시도가
   전부 사령관3~4 선에서 막혔다. 이는 각 위원의 실력 부족이 아니라 페이싱
   설계에서 비롯된 패턴으로 보이며, 실제 대회 심사(대개 수 분 단위)에서도 같은
   일이 벌어질 가능성이 높다 — README가 강조하는 차별점이 채점 테이블에 실제로
   반영될지 불확실하다.

2. **핵심 주장 하나가 개발팀 자신의 문서로 목표 미달이 확인된다.** "상성이 승패를
   가른다"는 이 게임의 정체성인데, 그 우위의 크기가 개발팀이 정한 기준(≥40%p)에
   못 미친다는 것이 저장소에 그대로 남아 있다. 완전히 실패한 것은 아니지만("도배
   보다는 낫다"는 3인의 실측으로 참), "충분히 크고 고르게 낫다"는 아직 미완성이다.

3. **AI 해커톤이 요구하는 "실제 LLM 산출물" 요건이 아직 미충족이다.** README가
   스스로 D-3 최우선 과제로 못박았고, 오늘(2026-08-06) 기준 저장소 상태로 직접
   확인한 결과도 `provenance.llm: 0` — 아직 완료되지 않았다.

세 가지 모두 **크래시나 진행 불가 버그가 아니라, 제출 전 반드시 닫아야 할 검증
공백**이라는 공통점이 있다. 그래서 "보류"가 아니라 "조건부"다 — 게임 자체는
안정적으로 작동하고 핵심 주장의 방향은 맞지만, 대회가 직접 심사하는 세 가지 축
(후반 콘텐츠, 상성 밸런스, AI 콘텐츠 생성 요건) 각각에 미완료 꼬리표가 남아 있는
채로 제출하면 감점을 피하기 어렵다.

- **승/패 배너 색 미분리.** `BAN_CAMPAIGN`("원정이 끝났다")은 완주·패배 둘 다에서
  뜨는데 색이 늘 금색이었다. `feel.banner(code, win)`에 승패 플래그를 추가해
  패배 시 위험색(빨강)으로 갈랐다. "전투를 이겼다"(`BAN_STAGE`, 항상 승리만
  뜻한다)는 원래대로 금색이다.
- **첫 전투에 위기 신호가 없던 문제 — 절반만.** 원인은 `STAGE_HP_MUL[0]=2.6`
  (배열 최댓값, "판이 안 끝난다"를 고치려고 일부러 크게 둔 값 — config.js 주석
  참조)이 첫 전투 기지 체력을 다른 어느 전투보다 부풀려서였다. 그 값은 판
  길이 계약(40~60초)에 직결돼 있어 손대지 않았다. 대신 **물**(전투와 독립된
  둘째 위협축)을 건드렸다 — `STAGE_WATER_MUL[0]`을 0.70(다섯 칸 중 유일하게
  "기준보다 느린" 값)에서 1번 전투와 같은 0.95로 올렸다. 기지 체력·전투 길이는
  그대로 두고 물의 위기감만 살렸다 — 근본적인 "첫 전투가 안전하게 설계됐다"는
  사실 자체는 안 바뀐다.

**시도했다가 되돌렸다:**
- **신규 세션마다 다른 첫 별자리** (`game.setZodiacSeed(Date.now())`, 우선순위
  5번). `tools/evaluate.mjs`가 `game.js`를 직접 import하는 게 아니라 실제
  브라우저로 `index.html`/`main.js`를 그대로 띄운다는 것을 놓쳤다 — 이 한 줄이
  평가기의 봇도 똑같이 거치면서 씨앗을 흔들었다. 그런데 config.js 309번째 줄
  주석이 이미 실측해 둔 대로 **씨앗 0은 상성 봇에게 최상단 표본**이다(6벌
  평균보다 유리) — 격차 40%p 게이트 자체가 그 표본 위에 정의돼 있다. 격리
  트리 재측정에서 상성−도배 격차가 +40%p → **−20%p**로 뒤집히고 상성 삼각형
  동금도 6→5로 깨져 즉시 되돌렸다. 안전하게 고치려면 평가기에 test-mode
  플래그(예: `?seed=0` 쿼리 파싱)가 먼저 필요하다 — QA 게이트 자체를 건드리는
  별도 작업이라 범위 밖으로 남겼다.

**손대지 않았다 (의도적으로):**
- **`tools/bake.js`의 실전 LLM 베이크** (우선순위 3번). `OPENAI_API_KEY`가 이
  작업 환경에 없다 — 만들어 내거나 대신 다른 키를 쓰지 않았다. 다만
  `node tools/verify-chunks.js`는 이번에 실제로 돌려 확인했다: 현재
  `data/chunks.json`(저술 350/350, `provenance.llm:0`)에 대해 **통과**한다
  (스키마·상성 대응·구성 분산·중복률 전 항목 `[ok]`). 즉 "출처를 속이지 않는다"는
  계약은 지켜지고 있고, 남은 것은 문자 그대로 `OPENAI_API_KEY=... node
  tools/bake.js`를 실행하는 것뿐이다 — 이건 팀이 직접 해야 한다.
- **후반 콘텐츠 도달성 / 사령관3("금고") 난이도 절벽** (우선순위 4번, 가장 임팩트
  크지만 가장 위험). config.js의 기존 주석이 이미 원인을 정확히 짚어 뒀다 —
  금고는 경제가 빨라 AI가 기계 시대(자가수리 능력)까지 먼저 가는데, 상성으로
  대응하는 봇은 강철 시대에 머무는 판이라 시대 격차가 벌어질수록 능력이 하나씩
  더 붙는다("규칙대로다, 버그가 아니다"). 그 주석은 "고치지 않는다"고 명시적으로
  결론 낸 상태였다 — `무뇌원정완주 0/8` 게이트를 지키는 트레이드오프 축이기
  때문이다. 이번 보고서는 그 벽에 **적응형 전략까지도** 막힌다는 새 증거를
  더했을 뿐, 그 트레이드오프 자체를 재검토할 근거는 아니다 — 되돌리기 어려운
  경제 재조정 대신, 붕괴 초입에 더 강한 경고를 주는 정보성 접근(리뷰 본문의
  "해석이 갈린 지점" 절 제안)을 다음 라운드의 후보로 남긴다. 전용 측정
  라운드가 필요하다.

###### AI 활용 평가

우상단 `AI` 토글(좌표 약 930,28)로 디렉터 뷰를 매 세션 확인했다. 켜면 좌측에 5축 슬라이더(공격성·비축·경제·물량·상성 우위)와 임계선 표시, "보는 것"(플레이어 구성 아이콘 6개), "지시"(다음 웨이브 구성 아이콘, 강조색), 판정 간격(ms)·수위 배수 숫자가 실시간으로 뜬다.

**프로파일 판정이 실제 행동을 따라간다는 것을 3가지 서로 다른 플레이 스타일로 교차 확인했다.** 완전 유휴 플레이는 최종 프로파일 "수비형"(TURTLE)로 판정됐고(스크린샷 31), 궁수만 연타(구매 쿨다운으로 골드가 쌓이는 패턴)는 "물량형"에서 "경제형"으로 전환됐다(로그: iter325→iter350에서 SWARMER→ECONOMIST 전환, 골드가 137→250으로 쌓이는 시점과 정확히 일치). 콘솔에서 `director` 객체를 25틱 간격으로 직접 덤프해도 값이 매번 갱신되는 살아있는 상태임을 코드 레벨로도 재확인했다.

드래프트 화면의 "디렉터가 이 셋을 고른 이유"는 연출 문구가 아니라 그 순간 슬라이더 위치(공격성·물량이 우측 끝)와 실제로 부합했다(스크린샷 11, 44, 58). 다만 청동 진입과 강철 진입 두 세션에서 **동일한 문장**("숫자로만 밀고 있다 — 한 방을 준다")이 재사용된 것도 확인했다 — 판정 자체는 매번 재계산되지만, 그걸 사람에게 읽어 주는 문구 풀은 제한적으로 보인다.

사령관별 성향 차이(무리=물량형은 초반부터 값싼 유닛 위주, 쇄도=돌격형은 빠른 압박, 금고=경제형은 후반 폭발적 물량 폭발)는 실측으로 뚜렷했다. **다만 "내가 검사만 사면 적이 궁수를 늘린다" 식의 완전히 통제된 단일변수 카운터 실험까지는 시간상 못 했다** — "지시" 패널이 매 순간 다른 유닛을 강조하는 것은 확인했지만, 이게 순수히 내 조합에 대한 카운터인지 사령관 고유 성향과의 혼합 결과인지 분리 검증은 못 했다. 종합하면 **연출보다는 판단에 가깝다** — 서로 다른 스타일에 서로 다른 라벨이 정확히 붙었고, 근거 슬라이더와 텍스트가 모순되지 않았다는 것이 그 근거다.

###### 가장 좋은 것 세 가지

1. **디렉터의 판단이 화면에서 검증 가능하다.** 드래프트 카드 밑에 뜨는 "디렉터가 이 셋을 고른 이유"가 그 순간의 슬라이더 값과 실제로 일치했고(스크린샷 11: 공격성 낮음·물량 높음 상태에서 "숫자로만 밀고 있다" 판정), 3가지 다른 플레이 스타일에서 서로 다른 라벨(수비형/물량형/경제형)이 정확히 붙었다. 대회가 AI 활용을 심사한다면 이 화면이 설명 열 줄보다 강하다.

2. **상성·진화가 실제로 승패를 가른다는 것을 직접 대조 실험으로 재현했다.** 궁수 단일 도배(진화 미사용)는 사령관2에서 반복 패배했지만, 카운터에 반응하며 진화하는 봇은 같은 사령관을 22.4초 만에 완파했다. 저장소 내부 문서(`docs/strategic-depth.md`)는 개발 중기에 "유닛 선택이 결과를 안 바꾼다"는 진단을 남겼지만, 그 이후 spec-v4(30종 유닛 분화, 역할 기반 기지피해)를 포함한 약 35개 커밋이 이를 고쳤고 — 내 실측이 그 수정이 실제로 작동함을 증명한다.

3. **에셋 0개 제약이 핑계가 아니라 스타일이 됐다.** 돌 시대의 따뜻한 낮 팔레트(스크린샷 09)와 강철 시대의 차가운 밤 팔레트(스크린샷 62)가 같은 캔버스 도형만으로 확연히 다른 인상을 준다. 밝기=진영/색상=병종 구분과 위협색(분홍)의 배타적 사용이 94장의 스크린샷 전체에서 일관되게 지켜졌다.

###### 가장 나쁜 것 세 가지

1. **디렉터 뷰 패널이 내 기지를 통째로 가린다.** `src/render.js` 6210행 `drawDirectorView(x=UNIT*2=16, y=96, w=250, h=288)`가 화면 좌상단(x:16~266, y:96~384)을 차지하는데, 이 자리가 정확히 플레이어 기지 스프라이트 자리다(스크린샷 52·58·62·63에서 내 기지가 안 보이고 숫자 HP만 남는다). 심사에서 반드시 켜라고 안내하는 그 화면이, 심사에서 반드시 봐야 할 "내 기지가 얼마나 위험한가"를 가리는 셈이다. 패널을 반투명하게 하거나 기지가 없는 위치(예: 화면 중앙 상단)로 옮겨야 한다.

2. **첫 전투가 사실상 무위협이라 도입부에 긴장이 없다.** 능동적으로 플레이한 3회 세션 모두 사령관1(무리) 전투에서 내 기지 HP가 거의 줄지 않았다(스크린샷 45: 40골드 시점에도 아군 5232/5232). "첫 전투는 이기라고 있다"는 설계 의도(README)는 이해하지만, 그 결과 첫 30초는커녕 첫 전투 전체에 "내가 질 수도 있다"는 신호가 없다. 초반에도 작은 예고성 스킬 하나 정도는 넣어 최소한의 긴장을 심어야 한다.

3. **사령관3(금고)에서 회복 불가능한 절벽형 붕괴가 나온다.** 기지 체력이 92%(4158)에서 0으로 떨어지는 데 9.6초(t=118.0s→127.9s, 스크린샷 61→63)밖에 안 걸렸다. 반응형 봇이 타워·증원을 계속 쓰고 있었는데도 막지 못했다 — 전선이 무너진 뒤 기지까지 도달하는 시간이 너무 짧아 "만회할 기회"가 실질적으로 없었다. 기지 체력이 특정 임계선을 넘을 때 더 강한 경고(색·소리)를 주거나, 붕괴 초입에 재정비할 여유(예: 짧은 무적 프레임 없는 완충 타이밍)를 검토해야 한다.

###### 만약 하루가 더 있다면 무엇부터

1. **실기기(모바일) 오디오·프레임·터치 검증** — 나도 헤드리스라서 못 봤고, 저장소 자체 체크리스트(`README.md` "사람이 해야 할 일")도 이걸 최대 리스크로 지목하고 있다. 심사 당일 판정을 뒤집을 수 있는 유일한 미확인 항목이다.

###### 판정: **조건부**

첫 30초 점수(13/20)가 절반 미만이 아니라서 그 규칙만으로는 강등 대상이 아니다. 그럼에도 조건부로 매기는 이유는 별개다 — **원정 후반부(사령관4·5, 보스, 최강병기)와 실기기 오디오·성능을 이 심사에서 전혀 검증하지 못했고**, 둘 다 이 게임의 핵심 판매 포인트(README가 직접 "제출 영상에 이 화면이 들어간다"고 명시한 디렉터 뷰, 그리고 사전과제 D-3 체크리스트가 스스로 "미확인 리스크"라 적어 둔 항목)이기 때문이다. 확인된 범위(사령관1~3, 헤드리스 환경) 안에서는 콘솔 에러 0건, 실제 전략적 깊이, 실시간으로 반응하는 AI 디렉터가 분명히 확인됐다.

###### AI 활용 평가

이 항목이 이 게임의 핵심 주장이고, 실측으로 가장 잘 뒷받침된 부분이다.

**적의 행동은 고정 스크립트가 아니다.** 도배(궁수 100%) 전략에서 `director.js`의 `levers.mix` 배열을 5회 이상 시점에서 폴링한 결과, 기병(궁수의 상성 우위 유닛, `config.js`의 `COUNTER[U_CAV][U_ARCHER]=2.5`) 가중치가 일관되게 20~25대로 치솟았고 다른 유닛은 0.5~4대에 머물렀다(`24_run2_spam_iter250` ~ `iter700` 전 구간에서 반복 재현). 같은 세션에서 다양한 전략을 쓴 Run 1에서는 디렉터가 부여한 플레이어 프로파일이 "물량형"(전투1 승리 시점) → "돌격형"(2번째 원정 진입 시점)으로 **실제로 바뀌는 것**을 `12_final_director_view.png`와 `09_battle1_over.png`를 대조해 확인했다. 이는 연출이 아니라 `metricAggro/metricHoard/metricEcon/metricSwarm` 네 지표 막대가 실시간으로 움직이며 만드는 결과다.

**판단 근거가 화면에 드러나고, 그게 사실과 일치한다.** 디렉터 뷰는 "보는 것"(플레이어 실제 구매 비율)과 "하는 것"(다음 웨이브 구성)을 같은 6칸 아이콘 행으로 나란히 보여준다. 도배 전략에서 "보는 것"이 궁수 칸만 채워지고 "하는 것"이 기병 칸만 채워지는 것을 직접 캡처했다(`24_run2_spam_iter600_battle1.png`) — 이건 사후 합리화가 아니라 `COUNTERS_OF` 테이블을 통해 실제로 계산되는 값이다. 드래프트 카드 화면에도 "디렉터가 이 셋을 고른 이유"라는 별도 문장이 붙어(`draft_b1_before_pick.png`: "숫자로만 밀고 있다 — 한 방을 준다") 판단 근거가 디버그 패널 밖 실제 플레이 화면에도 노출된다.

**한계**: (1) 사령관 기본 성격(`CMD_MIX`)과 디렉터 반응(`CMD_MIX_W=0.5`)이 반씩 섞이므로, 순수하게 "AI가 학습했다"기보다 "사령관 고정 성향 + 실시간 카운터 로직"의 조합이다 — 코드가 스스로 그렇게 문서화하고 있어 과장은 아니다. (2) 판정 자체는 `Math.random()`을 쓰지 않는 결정론 해시라 재현 가능하지만, 그 대가로 **첫 전투의 별자리는 모든 신규 세션에서 동일하다**(아래 "가장 나쁜 것" 참조) — "판마다 다르다"는 주장이 첫인상에서는 약해진다. (3) 계층2(오프라인 LLM 베이크, `data/*.json`)는 README에 스스로 "현재 오프라인 자리표시자"라고 적어놓았고 내가 실행한 두 판에서도 `data/*.json`을 별도로 검증하지 않았다 — 계층1(런타임 디렉터)만으로 위 결론을 냈다.

총점 76점(B), "첫 30초" 16/20은 배점의 절반(10점)을 넉넉히 넘겨 자동 강등 조건에 해당하지 않는다. 이 심사 관점(AI 활용)에서 핵심 주장인 "적이 플레이어 행동에 반응해 전략을 바꾼다"를 수치로 재현 검증했고, 콘솔 에러 0(Run 2 전 구간 실측), 게임을 멈추는 결함을 플레이 중 만나지 않았다. 다만 소리·프레임 손맛·보스/최강병기 이벤트는 내 테스트 환경(headless, 음소거, 빠른 진행)의 한계로 직접 확인하지 못했으므로, 제출 자체는 가능하나 위 세 가지("나쁜 것" 항목)는 제출 전 확인을 권한다.

###### 이 평가의 한계
- **소리를 듣지 못했다.** Playwright headless가 `--mute-audio`로 실행되어 오디오 관련 채점(3, 5번 항목 일부)은 전부 코드 리딩(`audio.js`)에 근거했고 실제 청취 검증이 아니다.
- **프레임 단위 입력 지연을 측정하지 못했다.** 60fps 녹화 장비가 없어 "입력→반응 몇 프레임"은 스크린샷 간격(약 350ms) 수준의 조악한 확인만 했다.
- **보스("심연")와 "최강병기" 소환을 명확히 목격하지 못했다.** Run 1의 5번째 전투(거울 사령관)를 봇이 너무 빠르게 통과해 관련 이펙트로 추정되는 주황 링만 캡처했고 확증하지 못했다.
- **결과 카드가 완전히 떠오른 화면(색 분리된 승/패 타이틀, 5-사령관 격파 매트릭스)을 직접 스크린샷하지 못했다.** 내 스크립트가 OVER 상태 감지 즉시 클릭해 넘어가 배너 단계만 포착했다. 존재는 코드로 확인했다.
- **계층2(오프라인 LLM 베이크, `data/*.json`)를 별도로 검증하지 않았다.** README 자체가 이를 "자리표시자"라고 명시하고 있어 계층1(런타임 디렉터)에만 집중했다.
- **모바일/실기기, 실제 신청자 관점(비개발자의 첫인상)은 확인하지 못했다.** 데스크톱 헤드리스 960×540 뷰포트 기준 결과다.

###### AI 활용 평가

우상단 `AI` 토글로 열리는 디렉터 뷰는 실제로 살아있는 제품 기능이었다. 상단 사령관 배지(예: "무리 / 물량형", 고정 정체성)와는 별개로 패널 안쪽에 "AI 디렉터 — 경제형"처럼 **다른 값**이 표시되는 것을 확인(`11_director_view_on.png`) — 이는 사령관의 고정 페르소나와, 나(플레이어)의 실시간 행동을 읽은 판정값이 분리된 두 층이라는 뜻이고, 두 값이 다르게 찍힌다는 것 자체가 후자가 실제로 계산되고 있다는 증거다. 패널에는 공격성·비축·경제·물량·상성우위 5개 지표 막대(임계값 눈금 포함), "보는 것"(내 실제 구성)과 "지시"(다음 웨이브 구성) 아이콘 행, 간격(ms)·수위배수 같은 구체적 수치까지 노출돼 연출이 아니라 판단 로그로 읽힌다. 드래프트 화면의 "디렉터가 이 셋을 고른 이유" 문구("숫자로만 밀고 있다 — 한 방을 준다")가 서로 다른 세션에서 동일한 내 플레이 패턴에 반복적으로 붙어 나온 것도 임의 문구가 아니라 판정에 종속된 텍스트임을 뒷받침한다.

행동 차이도 실측했다: 세션2에서 3번째 사령관("금고", 자기소개 "너는 지금 쓰고 나는 나중에 쏟는다")이 초반 내내 잠잠하다가 물병자리(스킬피해 +40%) 버프가 걸린 상태에서 약 10초 만에 내 기지를 4083에서 0으로 만드는 역전 러시를 실행했다(`64_run2_a2_r72_stage2.png`→`play2.log` handle-1). 반면 2번째 사령관("쇄도")은 게임 초반부터 지속적으로 밀어붙이는 느낌이었다(정성적 관찰). 다만 "내가 한 병종만 도배했을 때 실시간으로 카운터를 바꾸는가"는 통제된 단일변인 실험으로 확인하지 못했다(나는 창병+투석대 위주 혼합 조합을 유지) — 디렉터 패널의 "지시" 아이콘이 매 순간 바뀌는 것은 봤지만 그것을 내 조합 변화와 1:1로 대응시켜 검증하진 않았다.

한 가지 감점 요인: 저장소 README가 스스로 "D-3 전에 반드시 할 일"로 못박은 항목 — `data/*.json`을 `tools/bake.js`로 실제 LLM API 호출을 거쳐 만든 산출물로 교체하는 것 — 이 아직 완료되지 않은 것으로 보인다. `data/chunks.json`을 열어보면 `"generator":"authored:claude"`, `provenance:{"authored":350,"llm":0}`으로, 350개 웨이브 전부가 실시간 LLM 호출이 아니라 코딩 에이전트(Claude)가 직접 손으로 설계해 적은 상수다. 이는 `tools/authored-waves.js` 헤더 주석에 정직하게 명시돼 있어 은폐는 아니지만, README 자신이 "이대로 제출하면 'LLM이 만든 콘텐츠'는 사실이 아니게 된다"고 경고한 바로 그 상태에 가깝다. 플레이어가 실제로 만나는 "AI"(계층1 런타임 디렉터)는 정상 작동하지만, "오프라인 LLM 베이크"(계층2) 층은 아직 자체 기준을 통과하지 못한 상태다.

###### 가장 좋은 것 세 가지

1. **판정 근거가 화면에 숫자로 그대로 나온다.** `11_director_view_on.png`에서 5개 지표 막대(임계값 눈금 포함)와 "보는 것/지시" 아이콘, 간격 887ms·수위배수 1.0 같은 실수치가 노출된다. 게다가 이 값이 사령관 고정 배지("물량형")와 다르게 찍혀("경제형") 실시간 재계산임을 스스로 증명한다.
2. **사령관 성격이 연출이 아니라 사건으로 나타난다.** "금고" 사령관과의 전투에서 거의 이긴 판(적 기지 10%)이 10초 만에 내 기지 전파(全破)로 뒤집혔다(`play2.log` t=134.7~144.3s) — "너는 지금 쓰고, 나는 나중에 쏟는다"는 소개 문구가 그대로 게임 사건이 됐다.
3. **시대 진화가 이름·색·아이콘까지 실제로 바꾼다.** 돌도끼병→청동검사→강철기사, 투석대→발리스타로 유닛 자체가 다른 그림이 된다(`06_`/`12_`/`18_` 스크린샷 연속 비교). 여기에 원정 종료 화면의 병종 구성 막대그래프(`66_run2_over_1_stage2.png`)까지 더해져, 진행 상태를 숫자가 아니라 그림으로 되짚게 해준다.

###### 가장 나쁜 것 세 가지

1. **후반 콘텐츠(보스 심연·최강병기 거신·5번째 사령관 거울)를 3회 완주 시도·5분 52초 동안 한 번도 못 봤다.** `src/config.js`에 존재는 확인했지만 게임플레이로는 검증 불가. 무뇌 도배가 2전투에서 걸러지도록 설계돼 있어(README 자체 QA 수치) 짧은 심사 세션에서는 후반 콘텐츠에 아예 닿지 못하는 심사위원이 나올 위험이 크다. **개선안**: 심사용으로 스테이지 스킵/하이라이트 데모를 별도 경로로 열거나, `STAGE_HP_MUL`/`STAGE_DIFF` 초반 곡선을 살짝 낮춰 3~5번째 사령관까지 도달 시간을 단축하라.
2. **`data/*.json`이 아직 README 자신이 정한 "LLM 베이크 완료" 기준을 통과하지 못했다.** `data/chunks.json`의 `provenance.llm:0`을 보면 실제 API 호출 없이 코딩 에이전트가 손으로 채운 상태다. **개선안**: `OPENAI_API_KEY`로 `node tools/bake.js` 실행 → `node tools/verify-chunks.js`로 `generator` 필드가 placeholder/authored가 아님을 확인.

###### AI 활용 평가

디렉터 뷰(우상단 "AI" 토글)를 실제로 켜서 확인했다(스크린샷 04). 단순 라벨이 아니라 5개 지표(공격성·비축·경제·물량·상성 우위)를 막대+임계선으로, "보는 것(플레이어 구성)"과 "지시(다음 웨이브 구성)"를 같은 6칸 아이콘으로 나란히 보여주는 실제 대시보드였다. 판단 근거가 화면에 드러나는가에 대해서는 — 드러난다. 특성 드래프트 카드 화면 하단에 "디렉터가 이 셋을 고른 이유"라는 문구가 항상 붙는데, 내가 스테이지0(14.1초 시점)과 스테이지3(126.9초 시점)에서 똑같이 "숫자로만 밀고 있다 — 한 방을 준다"는 문구를 받았다(스크린샷 06, 12). 이건 스크립트가 아니라 실측 지표 반영이라는 정황 증거다 — 내가 실제로 6.5분 내내 유닛을 다양화하지 않고 스팸에 가깝게 구매했고, 그 결과 같은 판정이 반복된 것이다. 판정이 그럴싸한 연출이 아니라 실제로 내 행동에 연동돼 있다는 뜻이다. 결과 화면에서도 "프로파일: 물량형"으로 나를 판정해 보여줬고(스크린샷 09), 이는 `src/director.js`의 결정론적 해시 기반 판정 로직(`classify()`, 히스테리시스, `Math.random()` 미사용)과 일치한다.

###### 가장 좋은 것 세 가지

**1. 디렉터 뷰와 드래프트 사유 문구가 실제 판단의 증거를 화면에 낸다.** 우상단 AI 토글을 켜면 관찰 중인 4개 축과 임계선, "보는 것 vs 지시"가 같은 화면에 나란히 뜬다(스크린샷 04). 진화할 때마다 뜨는 특성 카드 하단의 "디렉터가 이 셋을 고른 이유"는 내가 스테이지0과 스테이지3에서 똑같이 스팸 플레이를 했을 때 똑같은 문구("숫자로만 밀고 있다 — 한 방을 준다")를 반복해서 보여줬다(스크린샷 06, 12) — 이건 연출이 아니라 실측 지표가 실제로 반영된다는 증거다.

**2. 시대 진화가 숫자가 아니라 종류를 바꾸고, 그게 전투 간 승계된다.** 돌→청동 진화 순간 유닛 이름이 "돌도끼병"에서 "청동검사"로 바뀌는 동시에 새 능력 "연합"(근처 다른 종류 아군 있으면 피해+30%)이 화면에 문장으로 표시됐다(스크린샷 07). 그리고 2차 원정 시도에서 4번째 전투(스테이지3) 진입 시점에 내 시대와 적 시대가 둘 다 이미 4(기계, 최대치)로 시작하는 것을 실측으로 확인했다 — 5회 전투를 다섯 번의 같은 판으로 만들지 않으려는 설계가 실제로 작동한다.

**3. 결과 화면이 "한 판 더"의 동기를 구체적으로 제시한다.** 스테이지0 승리 직후(스크린샷 09) 5개 사령관 로스터가 격파 표시(금색 X)와 다음 상대(흰 고리)로 갱신되고, 다음 상대의 도발 대사("생각할 시간을 주지 않겠다")가 미리보기로 뜨며, 내가 실제로 뽑은 유닛 구성과 AI가 매긴 내 플레이 프로파일("물량형")이 동시에 표시된다. 다음 판에 뭘 바꿔야 할지가 감이 아니라 데이터로 주어진다.

###### 가장 나쁜 것 세 가지

**1. 코어 루프의 핵심 주장("상성이 승패를 가른다")이 개발팀 자체 실측으로 목표 미달임이 문서에 남아 있다.** `README.md` 192-219행은 유닛 가격표를 √(전투력) 기준으로 재설계한 뒤에도 "상성−도배 격차는 −18%p → +3%p 에서 멈춘다 (목표 ≥40%p 미달)"이라고 명시하고, `docs/auto-improve-log.md` 228-231행은 별도 개선 이후에도 "여섯 종 전부로 재면 정직한 격차는 여전히 음수"이며 "기병 도배가 진짜 최강 도배(63%)인데 평가기가 안 본다"고 자백한다. 심사위원이 코드를 안 읽으면 몰랐을 문제지만, 문서가 스스로 남긴 만큼 가산점은 못 준다 — 고치려면 `src/config.js`의 U_COST/U_HP/U_DMG 값표를 다시 스윕하거나, `docs/strategic-depth.md` §7이 이미 제안해 둔 "제약(인구 상한)" 또는 "공간(전열 폭)" 축을 실제로 채택해야 한다(문서 자체가 "종합은 미완"이라고 적어 뒀다).

**2. 저장소에 다른 게임을 채점한 스테일 문서가 섞여 있다.** `docs/game-review.md` 전체가 "차오른다"가 아니라 이전 장르(러너·레인·코인·점프·슬라이드·부스트게이지)를 채점한 결과다 — README가 밝힌 "장르를 두 번 바꿨다(벽점프→러너→레인배틀)"의 잔재로 보인다. 채점 포맷(6항목 100점, "76/100 B+" 표)이 이 대회 채점 양식과 똑같아서, 심사자가 실수로 이 문서를 근거로 삼으면 완전히 다른 게임을 채점하게 된다. `docs/game-review.md`를 삭제하거나 최소한 "폐기됨/이전 장르"라고 파일 최상단에 표시해야 한다.

**3. 후반 콘텐츠(5번째 사령관 「거울」·보스 「심연」·최강병기 「거신」)를 6.5분 동안 확인하지 못했다.** 2차 원정 시도에서 스테이지2(금고/ECONOMIST)만 90초 이상 걸리며 예산이 끝났다 — `game.js:396`(`bossOn`)·`852`(`wpnEligible`)로 코드상 존재는 확인했지만, 실제 심사 시간 내에 도달 가능한지는 별개 문제다. 대회 심사가 보통 수 분 단위인 점을 고려하면, 후반부가 실제로 보여주는 차별점(README가 강조하는 5번째 전투의 보스·최강병기)을 심사자 다수가 놓칠 위험이 있다 — 페이싱을 앞당기거나 심사용 빠른 진입 경로가 필요하다.

###### 만약 하루가 더 있다면 무엇부터

1. **상성−스팸 격차를 목표(≥40%p)까지 끌어올리는 구조적 변경 하나를 실제로 채택한다.** `docs/strategic-depth.md` §7의 네 안(제약·정보·공간·시간) 중 가장 규칙이 적은 것 하나만 골라 넣는다 — 다 넣으면 안 된다고 문서 스스로 경고해 뒀다.
2. **원정 페이싱을 조정하거나 심사용 빠른 진입 경로를 만든다.** 5번째 전투(보스·최강병기)까지 심사 시간(5~10분) 안에 닿을 수 있어야, README가 강조하는 후반 차별점이 실제로 채점에 반영된다.
3. **`docs/game-review.md` 등 스테일 문서를 정리한다.** 삭제 또는 "폐기됨" 마킹, `tools/` 아래 수백 개 실험 스크립트(`bal-*.mjs`, `zzz-*.mjs` 등)도 정리 — 게임 로드에는 영향 없다지만 제출물 전체의 신뢰도를 흐린다.

###### 판정: 조건부

총점 76(B)이고 첫 30초가 배점의 80%(16/20)로 자동 강등 기준(절반 미만)에는 안 걸리지만, 이 게임의 핵심 셀링포인트(상성이 승패를 가른다)가 개발팀 스스로의 최신 실측으로 목표 미달임이 문서에 남아 있고, 후반 콘텐츠·실기기 성능·iOS 오디오가 README 자체에서도 "사람이 아직 확인 안 함"으로 체크되지 않은 채 남아 있다 — 완성됐다기보다 검증이 진행 중인 상태로 제출된 인상이다.

###### 이 평가의 한계

- **실기기(모바일) 미검증**: headless Chromium·데스크톱 뷰포트(960×540)만 사용했다. iOS Safari 오디오, 터치 제스처 차단, 실제 GPU 합성 프레임타임은 README 자체도 "사람이 해야 할 일"로 미확인 표시해 둔 항목이라 이 보고서도 검증하지 못했다.
- **오디오 인지 검증 불가**: headless 환경에서 실제 소리를 듣지 못했다. 절차합성 코드(`src/audio.js`)의 설계 의도는 읽었지만 "소리가 화면보다 먼저 알려주는가"는 청취로 확인하지 못했다.
- **원정 5전투 완주·보스·최강병기 미관측**: 6.5분·원정 2회 시도로 4/5 사령관까지만 실제로 겪었다. 5번째 사령관("거울")·보스("심연")·최강병기("거신")는 코드로만 확인했다.
- **동시 실행 환경 잡음 가능성**: 같은 샌드박스에 다른 심사 세션(예: `judge8823` 흔적)이 동시에 브라우저를 띄우고 있는 것을 프로세스 목록에서 확인했다. 판정 로직 자체는 결정론적 해시 기반이라 게임 로직에는 영향이 없어야 하지만, CPU 경합으로 인한 타이밍 잡음(프레임 처리 지연 등) 가능성은 완전히 배제하지 못한다.
- **`data/*.json`의 정확한 생성 경로 미확인**: `chunks.json`의 `generator` 필드가 `"authored:claude"`(LLM 저작, placeholder 아님)로 표기된 것은 확인했지만, 이것이 README가 요구한 `tools/bake.js` + 실제 API 키 파이프라인을 통과한 결과인지, 개발 중 다른 경로로 채워진 것인지는 구분하지 못했다.
